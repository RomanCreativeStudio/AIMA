# AIMACore

The platform-agnostic half of every AIMA client (Phase 2.1, `docs/decisions/0009-macos-experience-foundation.md`): typed API models, the networking layer, and view models. No dependency on SwiftUI/AppKit/UIKit — everything here is plain Swift + Foundation, so it builds and tests identically on macOS, iOS, tvOS, or (for verification without Xcode) Linux.

`apps/macos/` depends on this package and adds only its own SwiftUI views and app entry point; `apps/ios/` and `apps/tvos/` are expected to do the same once their own sprints begin (`docs/DEVELOPMENT_SETUP.md` §3: "Shared Swift code between `macos/` and `ios/` lives in a shared package").

## Structure

- **`Sources/AIMACore/Models/`** — `Codable`/`Identifiable`/`Equatable` structs mirroring the backend's JSON response shapes exactly (field names already match — the backend's own `map*Row` functions produce camelCase, so no key-conversion strategy is needed): `UserProfile`, `Workspace` (+ `WorkspaceSlug`/`WorkspaceType`), `Conversation`, `Message` (+ `IntentAnalysis`, `SendMessageResult`), `TaskItem` (+ `TaskStatus.displayName`), `PendingApproval`/`ApprovalDecision`, `Preference`, `SystemHealth`, `WorkspaceIntegration` (+ `IntegrationProvider`/`IntegrationStatus`/`IntegrationCapability`, Phase 2.3), `Workflow.swift` (+ `WorkflowKey`/`WorkflowRunStatus`/`WorkflowStepStatus`/`WorkflowStepDefinition`/`WorkflowDefinition`/`WorkflowStepRun`/`WorkflowRun`/`WorkflowRunDetail`/`WorkflowSuggestion`, Phase 2.4 — `WorkflowRunDetail` duplicates `WorkflowRun`'s fields flat rather than composing it, since the backend's `steps` field is a sibling, not nested under a `run` key), `Memory.swift` (+ `MemoryScope`/`MemoryRecord`/`RankedMemoryResult`, Phase 2.5 — the first fixed memory type in this package; `SendMessageResult.retrievedMemories` stayed a loosely-typed `[JSONValue]` since Phase 2.1 because nothing rendered it structurally until Conversation Intelligence's related memories needed one), `ActionLogRecord.swift` (+ `ActionOutcome`, Phase 2.5), `Briefing.swift` (`DailyBriefing`, Phase 2.5), `TaskIntelligence.swift` (+ `RelatedTaskGroup`, Phase 2.5), `ConversationIntelligence.swift` (Phase 2.5), `WorkspaceInsights.swift` (+ `ActivityMetrics`/`WorkflowMetrics`/`ApprovalMetrics`/`TaskCompletionMetrics`, Phase 2.5 — `WorkflowMetrics.byStatus` is `[String: Int]`, not enum-keyed, matching every other freeform-keyed dictionary already in this package), `Execution.swift` (+ `ExecutionStatus`/`ExecutionRecord`/`ExecutionPreview`/`ExecutionSuggestion`/`CreateExecutionRequest`, Phase 2.6 — reuses `IntegrationProvider` rather than duplicating it, and `requestPayload`/`responseSummary` stay `[String: JSONValue]` since their shape varies per `actionType`, the same reasoning as every other freeform JSONB field here). `JSONValue.swift` represents the backend's freeform JSONB fields (`preferences`, `assistantBehavior`, `metadata`, approval `payload`, workflow step `output`) where a fixed Swift type would be speculative; its `displayString` (Phase 2.2) renders one recursively for the Approvals detail screen.
- **`Sources/AIMACore/Networking/`** — `APIClient` (a protocol, mirroring the `AIProvider`/`EmbeddingProvider`/`IntentClassifier` provider-abstraction pattern already used in `backend/`/`ai-engine/`), `URLSessionAPIClient` (the real implementation), `APIError` (a closed, typed error set with user-facing messages).
- **`Sources/AIMACore/Configuration/APIConfiguration.swift`** — environment configuration (backend base URL, request timeout); reads `AIMA_API_BASE_URL` if set.
- **`Sources/AIMACore/Mocks/MockAPIClient.swift`** — an in-memory `APIClient` seeded with sample data across all four fixed workspaces, for SwiftUI previews and ViewModel tests. An `actor`, mirroring how `ai-engine`'s `MockProvider`/`MockEmbeddingProvider` stand in for a real provider in backend tests. `forceNextMessageToRequireApproval` (Phase 2.2) is a test-only hook that makes the next `sendMessage` call simulate a Tier 3 capability being triggered — something no capability's shipped default does yet — so the Chat screen's approval card has something real to fetch and test against. `forceNextMessageToSuggestWorkflow` (Phase 2.4) and `forceNextMessageToSuggestExecution` (Phase 2.6) are the same idea for the workflow- and execution-suggestion cards. The mock's workflow methods reimplement `WorkflowService`'s one-step-at-a-time state machine in-memory (including a real `PendingApproval` seeded for the one gated step, `read_email`), so `WorkflowsViewModel` tests exercise genuine state transitions, not canned responses. Phase 2.5's four Productivity Intelligence methods reimplement the backend's pure `taskAnalysis.ts`/`workspaceInsightsService.ts` helpers as private static functions and compute their results from the same seeded `tasksByWorkspace`/`approvalsByWorkspace`/`workflowRunsByWorkspace` state everything else reads — genuine computation over the mock's current state, not canned responses. Phase 2.6's five execution methods reimplement `ExecutionService`'s state machine the same way: `createExecutionRequest` seeds a real `awaiting_approval` `PendingApproval` (every built-in execution action type is Tier 3), and `executeExecution` re-checks that approval and the integration's connected status fresh on every call — idempotent on a terminal `succeeded`/`failed` record, exactly like the real `ExecutionService.execute`.
- **`Sources/AIMACore/ViewModels/`** — `DashboardViewModel` (Phase 2.5: loads `dailyBriefing`/`taskIntelligence`/`workspaceInsights` alongside the existing workspace/health/approvals/tasks), `ChatViewModel` (Phase 2.4: `lastWorkflowSuggestion`, cleared on conversation switch; Phase 2.5: `conversationIntelligence` + `loadConversationIntelligence()`, fetched only on explicit call — never automatically alongside `sendDraftMessage`, per that phase's "no automatic actions" rule; Phase 2.6: `lastExecutionSuggestion`, cleared on conversation switch the same way), `WorkspaceViewModel`, `SettingsViewModel`, `ApprovalsViewModel`, `TasksViewModel` (Phase 2.2: a full, filterable approvals list with detail, and a full, filterable task list), `IntegrationsViewModel` (Phase 2.3: connect/disconnect/rotate a workspace's connection to Gmail/GitHub/Calendar), `WorkflowsViewModel` (Phase 2.4: definitions, run history, a selected run's step detail, and create/execute-next-step/pause/resume/cancel — `executeNextStep` only ever advances one step per call, mirroring the backend's `WorkflowService`), and `ExecutionsViewModel` (Phase 2.6: execution history, a pending preview awaiting confirmation, a selected execution's detail, and `requestPreview`/`confirmPendingPreview`/`executeSelected` — `executeSelected` only ever advances one attempt per call, and is idempotent once the execution reaches a terminal status, mirroring the backend's `ExecutionService`). Built with the `Observation` framework's `@Observable` macro, **not** Combine's `ObservableObject`/`@Published` — Combine has no Linux implementation, and this package needs to build and test on Linux. `@Observable` is fully cross-platform and is what current SwiftUI/Xcode versions expect anyway.

## Testing

```bash
cd apps/Shared/AIMACore
swift build
swift test
```

Runs on macOS, or on Linux with a Swift 5.10+/6.x toolchain installed (`https://www.swift.org/install/linux/`) — no Xcode required. `Tests/AIMACoreTests/` covers model decoding (each fixture copied from a real backend response, not invented), `URLSessionAPIClient` (a custom `URLProtocol` intercepts requests — no real network or backend needed), and every view model against `MockAPIClient`.

Not every Apple-platform API is available in this Linux Foundation, though — `AttributedString(markdown:)` (used by `apps/macos`'s Chat screen for Markdown responses) isn't, confirmed by a failed trial build, so that one piece of Markdown rendering had to move to `apps/macos` itself rather than live here as a tested helper (`apps/macos/README.md`'s "Known limitation" section).
