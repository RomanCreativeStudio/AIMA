# ADR 0019: Advanced Memory System

**Status:** Decided
**Date:** 2026-07-28
**Relates to:** `docs/decisions/0001-memory-scope-model.md` (see `database/migrations/0002_memory_scopes.sql`), `backend/src/memory/`, `ai-engine/src/memory/`, `backend/src/conversation/conversationService.ts`, `apps/Shared/AIMACore/`, `apps/macos/`

## Context

Phase 1.2 gave AIMA plain memory storage and cosine-similarity retrieval, scoped by `scope` (`user`/`workspace`/`conversation`/`project`). Phase 3.4 asks to upgrade that into an *intelligent* memory system — importance/confidence scoring, ranking, lifecycle handling, an extraction pipeline that detects facts/preferences — while explicitly forbidding two things: autonomous behavior (no memory should be created without an explicit request) and hidden storage (nothing sensitive gets saved just because it was said). Everything below is designed around satisfying the scoring/ranking/lifecycle asks without ever letting a chat turn silently write to `memory_records`.

## Decisions

### 1. `scope` already is "memory categories" — `memory_type` is a new, orthogonal lifecycle dimension, not a replacement

The phase prompt asks for both "memory categories" and support for "short-term memory, long-term memory, workspace memory, user preference memory." The existing four-value `scope` enum already distinguishes *where* a memory belongs (user/workspace/conversation/project) — adding a second, competing category column would just fragment that concept. `database/migrations/0017_memory_intelligence.sql` instead adds only `memory_type` (`short_term` | `long_term`, default `long_term`), a genuinely new dimension: how long a memory should live, independent of which scope it's filed under. A `short_term` memory can carry an `expires_at`; once past, `MemoryService.search()`'s active-memory filter excludes it (`archived_at IS NULL AND (memory_type = 'long_term' OR expires_at IS NULL OR expires_at > now())`), while `long_term` memories never expire on their own.

### 2. Every new column is nullable or defaulted — no backfill, no existing row invalidated

`importance_score REAL NOT NULL DEFAULT 0.5`, `confidence_score REAL NOT NULL DEFAULT 1.0`, `memory_type memory_type NOT NULL DEFAULT 'long_term'`, plus nullable `last_accessed_at`/`expires_at`/`archived_at`. Every memory written by Phases 1.2–3.3 becomes readable and rankable the moment the migration runs, with no data migration step — a row inserted with only the pre-3.4 columns present defaults to a moderate-importance, fully-confident, long-lived, unarchived memory. `CHECK` constraints pin both scores to `[0, 1]`; `idx_memory_records_active` (partial, `WHERE archived_at IS NULL`) keeps the new "exclude archived" filter cheap.

### 3. Ranking is two-phase: SQL narrows by embedding distance, a pure function re-ranks by a blended score

`MemoryService.search()` still uses the HNSW-indexed `embedding <=> $query` operator to pick the top `limit × 4` (capped at 50) candidates — cheap, index-backed, unchanged from Phase 1.2. Those candidates are then re-ranked in application code by `backend/src/memory/ranking.ts`'s `rankMemories()`, which blends `similarity * 0.6 + importance * 0.25 + confidence * 0.15` per candidate (`computeRelevanceScore`) and sorts descending before truncating to the caller's requested `limit`. Keeping the blend in a pure TypeScript function — no database access, no side effects — makes "memory relevance scoring" (item 3's explicit ask) unit-testable in isolation from Postgres, the same precedent `taskAnalysis.ts` and `WorkflowIntentMatcher` already set for scoring/matching logic in this codebase.

### 4. Archive is a soft delete; delete is a hard delete — deliberately two different operations

`MemoryService.archiveMemory()` sets `archived_at` and stops the memory from appearing in default `list`/`search` results, but it's still in the table and recoverable via `includeArchived: true`. `MemoryService.deleteMemory()` issues a real `DELETE`. The phase prompt lists both "archive memories" and "delete memories" as separate required operations, and giving them genuinely different semantics — recoverable vs. permanent — is what makes that distinction meaningful rather than two names for the same action.

### 5. Extraction is a pure, rule-based, advisory-only pipeline — it can never persist anything itself

`ai-engine/src/memory/RuleBasedMemoryExtractor.ts` mirrors `RuleBasedIntentClassifier`'s "no AI call, deterministic phrase matching" shape, but unlike intent classification's first-match-wins, `extract()` returns every matching rule, since one message can contain several facts/preferences ("My name is Roman. I always draft proposals in a formal tone." yields two `MemoryCandidate`s). Every candidate carries a `reason` string naming the phrase pattern that matched — the "explainable" requirement — and an `importance`/`confidence` pair the caller can inspect before deciding whether to save it. Critically, `RuleBasedMemoryExtractor` has no database handle and no method that writes anywhere; it is structurally incapable of creating a memory. `ConversationService.sendMessage()` attaches its output to the response as `memorySuggestions: MemoryCandidate[]` — the same "advisory, never auto-executed" pattern `workflowSuggestion`/`executionSuggestion` established in Phases 2.4/2.6. A suggestion is not a save: only a separate, explicit call to `POST .../memories` (the pre-existing create endpoint) ever writes a row. This is the mechanism that satisfies "no hidden memory creation" and "do not automatically save every conversation" — nothing in the send-message code path can reach `MemoryService.createMemory`.

### 6. `memoryExtractor` is an optional dependency defaulting to the real extractor — no test-file ripple

`ConversationServiceDependencies.memoryExtractor?: MemoryExtractor` defaults to `new RuleBasedMemoryExtractor()` inside the constructor, rather than becoming a mandatory dependency every existing test file must supply (the approach Phases 2.4/2.6 took for `workflowIntentMatcher`/`executionIntentMatcher`, when those suggestions were the primary feature being tested). `memorySuggestions` is additive: no existing test asserts its absence, so defaulting gives every current caller real extraction behavior for free, and the one existing schema test (`conversationService.test.ts`'s "matches the full response schema") only needed its expected-keys list updated, not new fixture wiring.

### 7. AIMACore extends `MemoryRecord`/`RankedMemoryResult` rather than renaming them to match the prompt's literal model names

The phase prompt asks for models named `Memory`, `MemoryCategory`, `MemoryScore`, `MemorySearchResult`. Renaming the existing, already-consumed `MemoryRecord` → `Memory` and `RankedMemoryResult` → `MemorySearchResult` would ripple through `ConversationIntelligence.swift`, `MockAPIClient.swift`, and their tests for a pure rename with no functional gain — this codebase's own "no premature abstraction, no unnecessary churn" convention argues against it. Instead: `MemoryRecord`/`RankedMemoryResult` gain the new scoring/lifecycle fields (as `Optional`, defaulted in the memberwise initializer, so old fixtures still decode); `MemoryType` and `MemoryCategory` are added as genuinely new enums (the prompt's "categories" maps to a suggestion's fact/preference kind, distinct from `MemoryScope`); `MemoryScore` is added as a cheap, display-only convenience struct pairing importance and confidence for the UI (not the backend's weighted `relevanceScore`, which also needs a query similarity the client doesn't have); `MemorySuggestion` mirrors `ai-engine`'s `MemoryCandidate` exactly, the same way `WorkflowSuggestion`/`ExecutionSuggestion` already do for their respective ai-engine types.

### 8. `SendMessageResult` decodes `memorySuggestions` leniently, defaulting to `[]` when absent

Because the backend's field is a true non-null array (`memorySuggestions: MemoryCandidate[]`, never omitted), the faithful Swift type is a non-optional `[MemorySuggestion]` — but Swift's synthesized `Decodable` would then fail on any payload missing the key, including the existing `ModelDecodingTests` fixture written before this phase. `SendMessageResult` gained a small custom `init(from:)` that `decodeIfPresent`s `memorySuggestions` and falls back to `[]`, keeping the type faithful to the backend's real shape while staying backward-decodable — the same posture `MemoryRecord`'s new `Optional` fields take, applied here via a custom initializer instead of Optional typing since the field's true type isn't optional.

### 9. Authorization and validation mirror the existing `drafts`/`tasks` routers exactly — no new gating scheme

The four new routes (`GET .../memories` list, `PATCH .../memories/:id` update, `POST .../memories/:id/archive`, `DELETE .../memories/:id`) validate workspace/memory UUIDs, reject out-of-range importance/confidence scores (`[0, 1]`, matching `MemoryService`'s own `assertUnitInterval`), and require at least one field on update — the same shape `drafts.ts`'s update/delete routes already use, which itself only gates *creation* through the `PermissionEngine`/`ActionLogger` (list/update/archive/delete are plain workspace-scoped writes). Extending that existing convention, rather than inventing new tiers for memory lifecycle actions, keeps "existing permissions" and "existing approval model" genuinely unchanged, as the phase's final requirements demand. `MemoryNotFoundError` (new, in `backend/src/memory/errors.ts`) reports identically for "no such memory" and "belongs to another workspace" — the same don't-leak-which-case reasoning as `ConversationNotFoundError`/`ExecutionNotFoundError`/`VoiceSessionNotFoundError`.

## Consequences

- `backend/`'s test suite grew from 509 tests (Phase 3.3's regression baseline, ADR 0018) to 540: `memoryService.test.ts` gained lifecycle/scoring/isolation/migration-backward-compatibility tests, a new `ranking.test.ts` covers `computeRelevanceScore`/`rankMemories` as pure functions, `routes/memories.test.ts` gained list/update/archive/delete route tests including cross-workspace 404 checks, and `conversationService.test.ts` gained two `memorySuggestions` tests (detection present, and an explicit assertion that `sendMessage` never inserts a row into `memory_records` on its own).
- `ai-engine`'s test suite grew from 42 tests to 51: a new `memory/` module (`RuleBasedMemoryExtractor.test.ts`, `ranking.test.ts`) covering fact/preference detection, multi-candidate messages, no-match cases, and score/reason validity.
- `apps/Shared/AIMACore`'s test suite grew from 154 tests to 176: new model-decoding tests (backward-compatible `MemoryRecord`/`RankedMemoryResult` decode, `MemorySuggestion` decode, `SendMessageResult`'s `memorySuggestions` defaulting), new `URLSessionAPIClient` tests for all six memory endpoints, and a new `MemoryViewModelTests` suite (load/filter/search/create/update/archive/delete, workspace isolation).
- The macOS app's module boundary was re-verified the same way ADR 0009/0017/0018 established: `swift build` inside `apps/macos` fails only on `no such module 'SwiftUI'`/`AppKit`, confirming the new `Views/Memory/` screen and its two sheets introduce no other compile error.
- No autonomous behavior was added: nothing outside an explicit user-initiated HTTP request (chat send, or a direct memory-management action) ever calls `MemoryService.createMemory`/`updateMemory`/`archiveMemory`/`deleteMemory`. `memorySuggestions` is read-only advisory metadata on the chat response.
- No hidden storage: memory creation still requires an explicit `POST .../memories` call; extraction only detects candidates, it never saves them.
- Workspace isolation, the existing approval model, and existing permission tiers are all unchanged — the new routes extend the same conventions `drafts`/`tasks` already established rather than introducing a parallel scheme.
