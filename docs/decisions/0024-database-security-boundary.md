# ADR 0024: Database Security Boundary (RLS Decision)

**Document ID:** ADR-0024
**Status:** Decided
**Date:** 2026-08-01
**Owner:** Lead Software Architect
**Reviewer:** Product owner
**Related Architecture:** `ARCH-001` §3 "Backend Architecture" (API Layer, Database), §6 "Workspace Architecture", §9 "Security Considerations" → "Data Protection", "API Security"
**Related Requirements:** `REQ-001` (Authentication)
**Related Documents:** `docs/decisions/0022-authentication-architecture.md` (`ADR-0022`), `docs/requirements/REQ-001-authentication.md`, `docs/governance/RISK-001-unauthenticated-endpoints.md`, `database/README.md`

## Context

EPIC-004 Sprint 4.9 (live verification against a real Supabase project) surfaced a Supabase security advisory: Row Level Security (RLS) is disabled on all 24 tables in the `public` schema. That sprint's report flagged this but explicitly declined to act — enabling RLS with no policies would have blocked all access, and the actual exposure hadn't been tested. EPIC-005 Sprint 5.1 exists to investigate that finding properly and make a documented decision, per `CONST-001` Article X ("the history of why decisions were made should never be lost") and Article XII (the Red Team Principle: actively search for weak assumptions before treating something as settled).

Two things needed establishing before any remediation could be chosen:

1. **How does AIMA's backend actually reach Postgres?** `ARCH-001` §3 already states the intended design — "The API layer is the only component allowed to talk to the database... Clients never call the... database directly" — but Sprint 4.9's report treated that as an assumption, not a verified fact about the live project's actual configuration.
2. **Is RLS-disabled a live, exploitable gap, or a cosmetic linter finding?** A Supabase RLS advisory fires for any table lacking RLS, regardless of whether that table is actually reachable from outside the project. Those are different severities and require different responses.

## Investigation Findings

**1. AIMA's own database access model.** `backend/src/db/pool.ts`'s `createPool` — the only production call site of `new Pool(...)` in the codebase (`grep -rl "new Pool(" backend/src` outside test files returns exactly this one file) — opens a direct `pg` (node-postgres) connection using `DATABASE_URL`, a plain Postgres connection string requiring a real database role and password. Every service (`UserService`, `WorkspaceService`, `TaskService`, `MemoryService`, etc.) receives this same `Pool` (or, in tests, a `Client`) through the shared `Queryable` type (`backend/src/db/queryable.ts`) and issues its own parameterized, `workspace_id`-scoped SQL. There is no `@supabase/supabase-js` dependency anywhere in `backend/package.json` or `backend/src`, no PostgREST client, and no code path that constructs a database call from the Supabase anon/publishable key — that key (`AUTH_PROVIDER_API_KEY`) is used exclusively by `SupabaseAuthProvider` (`backend/src/auth/supabaseAuthProvider.ts`) to call Supabase's Auth REST API (`/auth/v1/token`, `/auth/v1/logout`, `/auth/v1/.well-known/jwks.json`) — never Postgres or PostgREST. This confirms `ARCH-001` §3's design is what's actually implemented: the backend is the only application code that touches the database, and it does so with a role entirely distinct from the `anon`/`authenticated` roles PostgREST serves requests as.

**2. Existing security boundaries, layered above that single DB-access point.** `requireAuth` (account boundary — is this a legitimate, token-holding caller), `requireWorkspaceOwnership`/`requireUserOwnership` (workspace/user boundary — does the caller own the resource named in the URL, `ADR-0022` Decision 5), and `PermissionEngine.evaluate` (capability/tier boundary — is this specific action allowed to happen automatically, `ARCH-001` §5) are three separate, already-implemented layers, all enforced in application code before a query is ever issued. Underneath them, every workspace-scoped table carries `workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE` (verified across `0001_init.sql`, `0004_documents.sql`, `0007_drafts.sql`, `0009_preferences.sql`, `0011_integrations.sql`, `0012_workflows.sql`, `0014_executions.sql`, `0016_voice.sql`, `0019_embeddings.sql`) — a referential-integrity guarantee that every row belongs to a real workspace, though (correctly) not a row-level access filter by itself; the filter is the API layer's own consistent `WHERE workspace_id = $1` on every query, the mechanism `ARCH-001` §6 and §9 already call the workspace security boundary.

**3. The live project's actual exposure — tested directly, not assumed.** A direct `curl` against `https://cjdkijgwvirbbdkbtgjy.supabase.co/rest/v1/users` using only the anon/publishable key (a key Supabase designs to be shipped in client apps — not a secret) returned **HTTP 200** with a valid PostgREST response. `information_schema.role_table_grants` confirmed both `anon` and `authenticated` held full `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`TRUNCATE` grants (Supabase's un-revoked defaults) on all 24 `public` tables. Supabase's own advisor (`get_advisors`, security category) tags every `rls_disabled_in_public` finding `"facing": "EXTERNAL"` — its own classification confirms these tables are reachable from outside the project, not merely missing a best-practice setting. This is a real, live, currently-exploitable gap: anyone holding the anon key — which is not secret — could read and write every row of every AIMA table via a plain HTTP request, entirely bypassing `requireAuth`, `requireWorkspaceOwnership`, `PermissionEngine`, rate limiting, and the `action_log` audit trail. This directly contradicts `ARCH-001` §3's "clients never call the database directly," which this investigation had otherwise confirmed the backend itself respects — the violation was in the platform configuration, not the application.

**Conclusion on the three possible characterizations this sprint was asked to distinguish:** disabled RLS is **not** an intentional architecture decision (no ADR or `ARCH-001` text ever decided "expose Postgres via PostgREST"), and it is **not merely a temporary development convenience either** — testing showed it is presently a real, externally-reachable gap on the live project, not a theoretical one. It is an actual security gap, caused by leaving Supabase's default PostgREST/role-grant configuration untouched while building the application on the assumption (correct, for the application's own code) that only the backend would ever reach the database.

## Decision

**Option A: keep application-layer authorization as the system of record; do not adopt RLS.**

1. **Backend authorization remains the source of truth.** `requireAuth` → `requireWorkspaceOwnership`/`requireUserOwnership` → `PermissionEngine.evaluate` is the complete, already-implemented authorization chain (`ADR-0022`, `ARCH-001` §5/§6). No table gains a Postgres `CREATE POLICY`. This is not a gap being left open — Finding 1 established that the database is reachable, in this architecture, only through the one role the backend itself uses; there is no second, legitimate access path a `CREATE POLICY` would need to constrain. Building and maintaining a parallel row-level policy set that must be kept in sync with `PermissionEngine`'s capability/tier rules, `requireWorkspaceOwnership`'s ownership checks, and every future workspace-scoped table would be pure duplicated surface — a second place every future migration and every future authorization rule change must remember to update, with no user-facing benefit, directly against `CONST-001` Article II ("optimize for change," not accumulate parallel systems) and the Constitution's general bias toward the simplest mechanism that actually closes the gap.
2. **Why RLS specifically is not the right tool here:** RLS exists to make a table safe to query from a role that doesn't already carry the equivalent of `PermissionEngine`'s and `requireWorkspaceOwnership`'s logic — i.e., a role a client (browser, mobile app, or third party) can present directly, such as PostgREST's `anon`/`authenticated` roles. AIMA's application role (the one `DATABASE_URL` authenticates as) is not, and was never intended to be, such a role — it is the single trusted party Findings 1–2 describe, already carrying full authorization logic in front of every query. Enabling RLS on tables only that trusted role queries would add policy-authoring and -maintenance cost for a threat model (an untrusted role querying these tables directly) that Finding 3's fix (below) makes structurally impossible, not just discouraged.
3. **What actually prevents unauthorized access, going forward:** the same three application-layer checks (Decision 1) for anyone going through the API — which is the only sanctioned path — plus, closing Finding 3's real gap, **revoking the `anon`/`authenticated` roles' table/sequence/function grants on the `public` schema on the live Supabase project**, including `ALTER DEFAULT PRIVILEGES` so every future migration's new table is closed by default rather than needing a manual grant-revocation step remembered on each one. This was executed against the live project (`cjdkijgwvirbbdkbtgjy`) as part of this ADR, not deferred (Consequences, below, has the exact commands and verification). This is a role/grant change, not a row-level policy — it makes the `public` schema simply unreachable via PostgREST for both anonymous and authenticated-but-not-backend callers, which is the actual security property `ARCH-001` §3 already calls for. It is fully reversible (a `GRANT` restores prior behavior) and required no application code change, no migration file, and no test changes, since nothing in `backend/src` ever depended on those grants existing.
4. **Operational safeguard against regression:** `ALTER DEFAULT PRIVILEGES` (Decision 3) is schema-scoped and durable — it applies to tables created by future migrations automatically, so this fix does not silently lapse the next time `database/migrations/00NN_*.sql` adds a table. The Supabase security advisor (`get_advisors`, security category) will continue to report `rls_disabled_in_public` for every table, since the linter checks whether RLS is enabled, not whether grants make the table reachable — this is a known, accepted false-positive-for-this-architecture from this point forward (Risks, below), not evidence the gap re-opened.

## Alternatives Considered

- **Option B — introduce RLS with policies matching workspace ownership.** Rejected as unnecessary, not as unsafe. It would require: an `ADR` for the specific policy design, a migration enabling RLS and defining a policy per table (24 of them, some — `document_chunks`, `embeddings` — reachable only via a denormalized `workspace_id`, others — `integration_credentials`, `workflow_step_runs` — via a join to a parent row's `workspace_id`), a way for Postgres to know the calling application's authenticated user/workspace context (RLS policies read session state such as `current_setting()` or `auth.uid()`, which nothing in this backend's direct-`pg`-connection model currently sets), and a full test suite proving every policy matches `PermissionEngine`/`requireWorkspaceOwnership`'s existing rules exactly. That is real, ongoing engineering work solving a problem Decision 3's grant revocation already solves at the platform level, for a role (the backend's own) that was never going to be constrained by row policies as long as it remains the table owner / a `BYPASSRLS` role (confirmed: `SELECT rolbypassrls FROM pg_roles` shows the connection's role has `rolbypassrls = true`, the standard Supabase project-owner role) — meaning RLS policies would need `FORCE ROW LEVEL SECURITY` to even apply to it, a further deviation from how this architecture was built. Revisit only if the backend's own database-access model changes (e.g., a future move to per-request Postgres roles or direct client-to-Supabase access for some new client type) — at that point RLS would become the correct tool, not merely an available one, and would deserve its own ADR at that time.
- **Leave RLS-disabled as-is, documented but unremediated.** Rejected. Finding 3 is not a theoretical exposure; it is a live, unauthenticated, full-table read/write path around every one of this system's authorization layers. `CONST-001` Article IV (User Trust: security) and Article VII (least privilege) do not permit treating a confirmed, active gap as acceptable simply because remediating it wasn't RLS. This is also why this ADR's remediation was executed immediately rather than deferred to a "next phase" implementation sprint — the fix required no new code, migration, or architecture, only correcting a platform configuration that was never a deliberate decision in the first place.
- **Disable PostgREST/the Data API for this project entirely (Supabase project setting), instead of revoking grants.** Considered equivalent in spirit but not chosen as the primary fix: it is a dashboard/Management-API setting outside this session's available tooling (`Supabase` MCP tools operate at the SQL level — `apply_migration`/`execute_sql` — not project API configuration), and revoking grants achieves the identical practical outcome (PostgREST authenticates every request as `anon` or `authenticated`; with zero grants, every PostgREST request fails with `permission denied` regardless of whether the Data API itself stays enabled) while being expressible, auditable, and re-appliable as plain SQL. Worth doing in addition, as a defense-in-depth, operator-level step outside this ADR's SQL-expressible scope (Next Phase, below).

## Trade-offs

- **No database-level backstop if a future authorization bug ships in `PermissionEngine`/`requireWorkspaceOwnership`.** Under Option A, a bug in the application's own authorization logic is not caught by a second, independent layer (which RLS, done correctly, would provide) — it is caught by tests, code review, and this codebase's existing test suite discipline (isolation tests exist for every workspace-scoped service, per `docs/requirements/RTM.md`). Accepted: this is the same trade-off `ARCH-001` already made when it decided the API layer is the sole database gatekeeper rather than a defense-in-depth model: solo-developer maintenance cost is this project's scarcest resource (`ARCH-001` §8's guiding rule), and a second policy layer duplicating every authorization rule is exactly the ongoing cost that guiding rule exists to avoid paying without a corresponding, currently-real benefit.
- **The Supabase security advisor will keep flagging `rls_disabled_in_public` for all 24 tables indefinitely.** A future reviewer (human or automated) re-running `get_advisors` will see 24 `ERROR`-level, `EXTERNAL`-facing findings and, without this ADR, could reasonably conclude the gap Sprint 4.9 found was never fixed. Mitigated by this document existing and being linked from `RISK-001` and `database/README.md` (Consequences) — the advisor checks a mechanism (RLS), not the outcome (is the table actually reachable); this ADR records that the outcome was independently verified fixed by a different mechanism.

## Consequences

- **Applied to the live Supabase project (`cjdkijgwvirbbdkbtgjy`) as part of this ADR**, not deferred:
  ```sql
  REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM anon, authenticated;
  ```
  Verified immediately after: `curl` against `/rest/v1/users` with the anon key now returns `HTTP 401`/`permission denied for table users` (previously `HTTP 200`/`[]`); the same request bearing a freshly issued, real `authenticated`-role access token (from a live login) now returns `HTTP 403`/`permission denied for table users` (previously `HTTP 200`/`[]`). `information_schema.role_table_grants` confirms zero remaining `anon`/`authenticated` grants on any `public` table. The backend's own access (via its distinct, `BYPASSRLS`, table-owning role over `DATABASE_URL`) was not part of this grant set and is unaffected — re-confirmed by re-running an ordinary application-shaped query via the same access path immediately after.
- **No code, migration, or test changes required** — this ADR's remediation is entirely a platform/role-configuration change; `backend/src` and `database/migrations/` are unchanged by this decision. `docs/requirements/RTM.md`'s `REQ-001` row and `database/README.md` gain a pointer to this ADR (below) for discoverability; no new `DB-*` migration file was created, per this sprint's explicit "do not create unnecessary migrations" instruction — there is no schema change to express as one.
- **`RISK-001`** (closed in Sprint 4.9 for the authentication-endpoint exposure it registers) is unaffected by this ADR — it never covered database-level exposure. A new, narrower risk record is registered separately for the PostgREST finding (Risk Review, `docs/governance/RISK-002-...md`), reflecting that it is now `Mitigating`, not `Confirmed`, as of this ADR's live fix.
- **Future migrations remain safe by default** without a remembered manual step, per the `ALTER DEFAULT PRIVILEGES` statements above — a new table created by `database/migrations/00NN_*.sql` is not reachable by `anon`/`authenticated` unless a future ADR deliberately re-grants it (e.g., if a genuinely public, unauthenticated table were ever needed — none exists in this system today).

## Risks

- **The Supabase advisor's `rls_disabled_in_public` finding will persist and could be mistaken for an unfixed gap** by a future reviewer who doesn't cross-reference this ADR (Trade-offs, above). Mitigated by linking this ADR from `RISK-002`, `database/README.md`, and `RTM.md`; not eliminated, since the advisor itself has no mechanism to acknowledge a grant-based fix.
- **A future migration or a manually run `GRANT` could silently re-open this gap** — e.g., an operator following a generic Supabase tutorial that says "grant `anon` access to my table" without knowing this project's architecture deliberately keeps that role's access at zero. Not mitigated by tooling in this ADR; the mitigation is this document plus `database/README.md`'s pointer to it, so the reasoning is discoverable before someone re-grants access. A future automated check (e.g., a periodic `get_advisors`/grant audit) is a reasonable Sprint 5.2+ candidate (Next Phase) but is out of this sprint's scope.
- **This ADR's fix was verified against the `anon` role and one live `authenticated`-role token, not against `service_role`.** `service_role` (which does bypass RLS and, per Supabase's design, is meant to bypass these grants too) was not touched and was never in scope — this codebase does not use it anywhere (Finding 1), and revoking from it would not be meaningful since Supabase's PostgREST layer does not accept it as a caller-presentable credential the way `anon`/`authenticated` are. Not a risk this ADR introduces, noted for completeness.
- **Revocation-latency risk from `ADR-0022`** (a stolen access token remains valid for up to 15 minutes after revocation) is unrelated to and unaffected by this ADR — noted only to avoid this document being read as having changed that separate, already-accepted risk.
