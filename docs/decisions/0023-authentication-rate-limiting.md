# ADR 0023: Authentication Rate Limiting

**Document ID:** ADR-0023
**Status:** Decided
**Date:** 2026-08-01
**Owner:** Lead Software Architect
**Reviewer:** Product owner
**Related Architecture:** `ARCH-001` §3 "Backend Architecture" ("A single backend service"), §8 "Technology Recommendations", §9 "Security Considerations" → "Authentication"
**Related Requirements:** `REQ-001` (Authentication), acceptance criterion 5
**Related Documents:** `docs/decisions/0022-authentication-architecture.md` (`ADR-0022`), `docs/requirements/REQ-001-authentication.md`, `docs/requirements/REQ-001-implementation-plan.md` (`REQ-001-PLAN`), `docs/governance/RISK-001-unauthenticated-endpoints.md`

## Context

`ARCH-001` decided, from the start, that authentication endpoints must be rate-limited ("mitigate credential-stuffing/brute-force attempts, even in a single-user system" — §9). `ADR-0022` (EPIC-004 Sprint 4.3) operationalized every other piece of `ARCH-001`'s authentication design — provider, token model, device/session storage, identity mapping, workspace authorization — but deliberately left rate limiting undecided. `REQ-001-PLAN` names the open question directly: "Criterion 5 (rate limiting) requires deciding whether this is enforced by the managed provider, an API gateway, or in-process middleware — not decided here."

By EPIC-004 Sprint 4.6, `POST /api/auth/login` and `POST /api/auth/refresh` exist as real, reachable HTTP endpoints (`backend/src/routes/auth.ts`) with no rate limiting at all — the exact gap `ARCH-001` §9 and `REQ-001` criterion 5 require closed before that surface can be considered complete.

## Decision

1. **Mechanism: in-process, in-memory, not the managed provider or an API gateway.** `backend/src/middleware/rateLimit.ts`'s `RateLimiter` is a small fixed-window counter (a `Map<string, { count, resetAt }>`) living inside the backend process itself. This is justified by `ARCH-001` §3's own statement of the current architecture — "A single backend service" — not a fleet of horizontally-scaled instances behind a load balancer. A single process is the only writer to its own rate-limit state, so there is no need for a shared store (Redis or otherwise) to keep counters consistent across instances. This also matches `ARCH-001` §8's guiding rule that solo-developer operational surface is the scarcest resource: no new managed service, no new infrastructure dependency, no new operational surface to run or pay for.
2. **Algorithm: fixed window, not sliding window or a token bucket.** Simpler to implement, reason about, and test. The imprecision at a window boundary (a caller could in principle make close to `2 * max` attempts spanning two adjacent windows) is accepted — this is a credential-stuffing/brute-force defense for a single-account system, not a precise API-billing throttle, and the imprecision doesn't meaningfully change the defense's effectiveness at the thresholds chosen below.
3. **What's rate limited, and by what key:**
   - `POST /api/auth/login` is limited **two ways**: by normalized email alone (primary — catches a distributed brute-force attempt against the one real account regardless of which IP it comes from) and by source IP alone (backstop — catches a flood of requests, malformed or otherwise, that never accumulates against any single email bucket). Both checks run on every request; either can reject it.
   - `POST /api/auth/refresh` is limited by source IP alone. It carries no email to key on, and keying by the refresh token itself would be useless (an attacker fully controls which token they present, and legitimate rotation changes the token on every successful call, so a token-keyed bucket would never accumulate). A stolen/reused refresh token is already caught by `SessionService.refresh`'s own reuse-detection (`ADR-0022` Decision 2); this limiter is purely a resource-exhaustion backstop against a flood of refresh attempts.
   - `POST /api/auth/logout`, `GET /api/auth/sessions`, `DELETE /api/auth/sessions/:sessionId` are **not** rate limited. All three sit behind `requireAuth` (`backend/src/app.ts`) — an attacker without a valid access token cannot reach them at all, so brute-forcing credentials against them isn't a live threat the way it is for login/refresh.
4. **Thresholds:** login-by-email: 5 attempts / 15 minutes. login-by-IP: 20 attempts / 15 minutes. refresh-by-IP: 20 attempts / 15 minutes. Configurable via `AUTH_LOGIN_RATE_LIMIT_MAX`/`AUTH_LOGIN_RATE_LIMIT_WINDOW_MS`, `AUTH_LOGIN_IP_RATE_LIMIT_MAX`/`AUTH_LOGIN_IP_RATE_LIMIT_WINDOW_MS`, `AUTH_REFRESH_RATE_LIMIT_MAX`/`AUTH_REFRESH_RATE_LIMIT_WINDOW_MS` (`authRateLimitConfigFromEnv`, `backend/src/middleware/rateLimit.ts`) — same "dedicated small reader with safe defaults" shape as `createAuthProviderFromEnv` (`backend/src/auth/registry.ts`), not part of `loadConfig`'s fail-fast required set, since every default here keeps the app secure and running with no operator action required.
5. **Response:** `429 Too Many Requests` with a `Retry-After` header (seconds until the window resets), and a single generic body (`{ "error": "Too many attempts. Try again later." }`) regardless of which limiter (email or IP) tripped — so the response itself can't be used to distinguish "this account is being throttled" from "this IP is being throttled," consistent with login's existing generic-401 convention for not leaking account existence (`AuthLoginFailedError`, EPIC-004 Sprint 4.6).
6. **Reset on success:** a successful login clears both the email and IP buckets for that request; a successful refresh clears the IP bucket. A legitimate caller who mistyped a password a couple of times, or whose device refreshed while flaky network conditions caused a couple of failed attempts, isn't left soft-locked for the remainder of the window once they succeed.
7. **`trust proxy`:** `backend/src/app.ts` sets `app.set('trust proxy', 1)`. `ARCH-001` §8's recommended hosting platforms (Fly.io, Render, Vercel) all terminate TLS at an edge proxy; without this setting, Express's `req.ip` would resolve to that proxy's own address for every request, making the per-IP limiters effectively global (one shared bucket for all callers) instead of per-caller.

## Alternatives Considered

- **Redis or another shared/distributed store** — rejected for the current architecture. `ARCH-001` §3 describes a single backend service; a distributed store would add a new managed dependency, new operational surface, and new failure mode (what happens to rate limiting if Redis is unreachable?) to solve a consistency problem that doesn't exist yet, since there's only one process. Revisit if/when the backend is horizontally scaled to multiple instances — at that point, per-instance in-memory counters would under-count real attempts (an attacker spread across instances gets each instance's full budget), and a shared store becomes the correct next architectural decision, requiring its own ADR at that time.
- **A general-purpose npm rate-limiting package** (e.g. `express-rate-limit`) — rejected as unnecessary. The actual logic needed (a bucket per key, a window, a max, and a manual `reset`) is small enough to own directly, and owning it avoids a new dependency for something this codebase already has a strong "small interface, own implementation" pattern for elsewhere (`AuthProvider`, `OAuthProvider`, `SpeechToTextProvider`). Revisit if requirements grow past what a ~100-line class can reasonably cover.
- **Enforcement at the managed auth provider (Supabase Auth) or an API gateway** — rejected as the primary mechanism. Supabase Auth's own rate limiting (if any) is not part of the `AuthProvider` abstraction's contract and isn't something AIMA's code controls or can rely on being configured a specific way; an API gateway is infrastructure this single-service architecture doesn't otherwise have and would be a disproportionate addition solely for this. In-process middleware keeps the decision inside code this project already owns and tests.
- **Rate limiting `POST /api/auth/login` by IP+email combined into one key, instead of two separate checks** — rejected. A combined key means a distributed attack against the one real account from many different IPs would get a fresh bucket on every new IP, never accumulating — exactly the credential-stuffing scenario `ARCH-001` §9 names. Keying by email alone (Decision 3) closes that gap; the separate IP-only check is kept as a cheap backstop against non-account-specific flooding.
- **Counting only failed attempts toward the limit, not successes** — rejected as the base behavior; instead every attempt increments the counter (Decision 4), and only success clears it (Decision 6). Counting successes too still stops a fast automated script from hammering an endpoint with technically-correct requests; clearing on success is what actually protects a legitimate user from being penalized for their own earlier mistakes.

## Trade-offs

- **A caller who knows or guesses the real account's email can lock the legitimate user out of login for the rest of a 15-minute window**, by deliberately submitting wrong passwords for that email (Decision 3's email-keyed limiter has no source-IP dimension). This is the standard, accepted trade-off of any per-account rate limiter, and `ARCH-001` §"Authentication" frames this system's whole purpose as protecting the one real account, not preventing every possible self-inflicted denial-of-service against it — a stricter alternative (no per-account limiting) leaves the account open to the credential-stuffing risk this ADR exists to close, which is the worse trade for this system's actual threat model.
- **In-memory counters do not survive a process restart.** A restart (deploy, crash-restart) silently resets every bucket to zero. Accepted: rate limiting's job is to blunt a live, ongoing attack, not to provide a permanent record of past attempts; a restart-triggered reset is a minor, infrequent gap, not a security control this system depends on being perfectly continuous.
- **Fixed-window imprecision** (Decision 2): up to roughly `2 * max` attempts can occur across a window boundary. Accepted for the reasons stated in Decision 2 — this is not a precise throttle, it's a brute-force speed bump.

## Consequences

- `backend/src/routes/auth.ts`'s `AuthPublicRouterDependencies` interface requires three `RateLimiter` instances (`loginEmailRateLimiter`, `loginIpRateLimiter`, `refreshIpRateLimiter`), extending the base `AuthRouterDependencies` `authRouter` (logout/sessions) uses without them.
- `backend/src/app.ts`'s `AppDependencies.authRateLimiters` is optional (mirroring `sessionService`, EPIC-004 Sprint 4.6) so every pre-existing test/call site keeps compiling, but `authPublicRouter` (login/refresh) only mounts when **both** `sessionService` and `authRateLimiters` are present — the public auth surface can never ship without its abuse protection. `backend/src/index.ts`, the one real production call site, always constructs both.
- `backend/src/index.ts` constructs the three `RateLimiter` instances once, in the composition root, from `authRateLimitConfigFromEnv()` — the same dependency-injection shape every other service in this file already follows.
- No database schema change: rate-limit state is process memory only, never persisted, consistent with this being a live-attack defense rather than an audit trail (the `action_log` table already serves the audit-trail role for Tier 3/4 actions).
- `RISK-001` is not directly affected — its registered exposure (unauthenticated endpoint access) was already closed in EPIC-004 Sprint 4.5. This ADR closes `REQ-001`'s remaining acceptance criterion (5), a related but distinct concern (brute-force/credential-stuffing resistance on an endpoint that was always going to require *some* valid credential).

## Risks

- **Memory growth from many distinct keys** (e.g. a wide IP-scanning attack creating thousands of short-lived buckets) — mitigated by `RateLimiter`'s periodic sweep (an unref'd `setInterval` running once per window, deleting expired buckets), so memory is bounded by recently-active keys, not total historical keys.
- **Horizontal scaling would silently weaken this defense** (Alternatives Considered) — not mitigated here, since it doesn't apply to the current single-instance architecture; explicitly flagged as the trigger for a future ADR if/when the backend is scaled to multiple instances.
- **The email-keyed login limiter enables a self-inflicted lockout of the real account** (Trade-offs) — accepted, not mitigated further; noting it here so it isn't rediscovered as a surprise later.
