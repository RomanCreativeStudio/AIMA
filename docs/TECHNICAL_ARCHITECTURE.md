# AIMA Technical Architecture Document

**Version:** 0.1 (Founding Draft)
**Status:** Engineering Source of Truth — companion to `docs/PRODUCT_BIBLE.md`
**Owner:** Lead Software Architect
**Last Updated:** 2026-07-27

This document translates the AIMA Product Bible into an engineering blueprint. Where the Product Bible defines *what AIMA must be* (principles, permission tiers, workspace separation), this document defines *how the system is built* to deliver on those commitments. If any part of this architecture conflicts with the Product Bible, the Product Bible wins and this document must be revised.

---

## 1. System Overview

AIMA is a single logical assistant exposed through multiple client surfaces, backed by one shared backend, one shared data layer, and one AI orchestration layer. There is one user, one identity, and one continuous memory — but that memory and data are partitioned by workspace (Section 6) and gated by a permission system (Section 5) at every layer, not just in the UI.

```
                    ┌──────────────────────────────────────────────┐
                    │                  Clients                      │
                    │  macOS app · iPhone app · Web dashboard       │
                    │  (Future: Apple TV companion)                 │
                    └───────────────────┬────────────────────────────┘
                                        │ HTTPS / WebSocket (auth'd)
                    ┌───────────────────▼────────────────────────────┐
                    │                Backend API                     │
                    │  Auth · Workspace router · Permission engine   │
                    │  Action logger · Business logic (RCS/MFS/etc.) │
                    └───────┬───────────────────────┬────────────────┘
                            │                        │
                ┌───────────▼───────────┐  ┌─────────▼──────────────┐
                │   Database + Storage   │  │   AI Orchestration       │
                │  (workspace-scoped)    │  │  Model calls · Memory    │
                │                        │  │  Context · Retrieval     │
                └────────────────────────┘  └──────────┬───────────────┘
                                                        │
                                            ┌───────────▼───────────┐
                                            │   LLM Provider(s)      │
                                            │  (Claude API, etc.)    │
                                            └────────────────────────┘
```

**Core architectural commitments (non-negotiable, inherited from the Product Bible):**
- The backend — not the client, and not the AI model — is the enforcement point for permissions, workspace isolation, and logging. Clients render and collect input; they do not decide what's allowed.
- The AI model proposes; the backend disposes. A model output that implies an external action is never executed directly — it is always routed through the permission engine first.
- One codebase, one API, many thin clients. Business logic lives in the backend, not duplicated per platform.

## 2. Application Architecture

All clients are **thin, presentation-focused surfaces** over the same backend API. No client holds business logic, permission logic, or direct AI/database access. This keeps the multi-platform surface (macOS, iOS, web, future tvOS) sustainable for a solo developer.

### Shared approach
- **One shared codebase across Apple platforms** using Swift and SwiftUI (macOS + iPhone + future Apple TV share a single SwiftUI target with platform-specific view variants). This is the single highest-leverage decision in this document for a solo developer in the Apple ecosystem.
- Realized (Phase 2.1) as a two-package split: **`apps/Shared/AIMACore`** — a platform-agnostic Swift package holding typed API models, the `APIClient` networking abstraction (mirroring `ai-engine`'s `AIProvider`/`EmbeddingProvider` provider pattern), and `@Observable` view models, with no SwiftUI/AppKit/UIKit/Combine dependency — and thin, per-platform SwiftUI executable targets (`apps/macos`, later `apps/ios`/`apps/tvos`) that depend on it and add only views and an app entry point.
- **Web dashboard as a separate lightweight client**, same API, used for cross-platform access and quick browser-based interaction (e.g., from a work PC). Not a full feature-parity requirement in early versions — it can lag the native app.
- All clients authenticate the same way (Section 3) and render the same underlying concepts: workspaces, conversation, suggestions/drafts/pending-approvals, and activity log.

### macOS App
- Primary "power user" surface: full workspace switching, side-by-side drafts, deeper project/knowledge views.
- Long-lived, persistent connection to the backend for real-time AI responses and notifications.
- **Phase 2.1 (Experience Foundation, `docs/decisions/0009-macos-experience-foundation.md`)** delivered the first usable app: a `NavigationSplitView` (`RootNavigationView`) switching between four screens — **Dashboard** (active workspace, system health, pending approvals with approve/reject, tasks overview), **Chat** (conversation list, message history, input, detected-intent/approval banner), **Workspace** (switcher across Personal/RCS/MFS/Development), and **Settings** (backend URL, user profile/preferences). A `DependencyContainer` wires a real `URLSessionAPIClient` or, for previews/tests/local exploration without a backend, a seeded `MockAPIClient` (`AIMA_USE_MOCK_API=1`). No voice interface, external integrations, email sending, or automation execution — pure read/act-on-existing-data foundation, per that phase's scope.
- **Phase 2.2 (Daily Assistant Interface, `docs/decisions/0010-daily-assistant-interface.md`)** deepened three of Phase 2.1's four screens and added two new ones, still with no automation execution: **Chat** now renders assistant responses as Markdown and surfaces an inline **approval card** (approve/reject without leaving the conversation) whenever a turn's response carries a real, DB-backed approval, not just the advisory intent banner. **Tasks** (new) lists every task in the active workspace, filterable by status, each row showing a color-coded priority indicator. **Approvals** (new) is a full, filterable list-plus-detail view (payload, timestamps, approve/reject) beyond the Dashboard's pending-only quick list. `AIMACore` grew `ApprovalsViewModel`/`TasksViewModel`, `APIClient.getApproval` (the single-approval fetch the detail pane and chat card both need), and `JSONValue.displayString` (a recursive, human-readable rendering of a payload).
- **Phase 2.3 (External Integrations Foundation, `docs/decisions/0011-external-integrations-foundation.md`)** added a seventh screen, **Integrations**: a card per fixed provider (Gmail/GitHub/Calendar) showing connection status, its capability display (which actions it gates and at what tier), and connect/disconnect/rotate actions. Connecting or rotating opens a dynamic credential-entry sheet built entirely from the backend's own `requiredCredentialFields` list — the client never hardcodes which fields a provider needs, so a fourth connector added later needs no UI change. `AIMACore` grew `IntegrationsViewModel` and the `WorkspaceIntegration`/`IntegrationProvider`/`IntegrationCapability` models; `MockAPIClient` seeds one already-connected provider (GitHub) and two disconnected ones so the screen previews meaningfully without a backend.
- Because Phase 2.1 was built in a Linux-only environment, `apps/Shared/AIMACore` was compiled and its test suite run for real via `swift test`; the SwiftUI layer in `apps/macos` itself was written but could only be checked for manifest correctness (`swift package dump-package`) and that it fails solely on the expected `no such module 'SwiftUI'` (proving no hidden logic errors) — a genuine Xcode build/Preview pass on macOS is still outstanding. Phase 2.2 hit the same constraint a level deeper: `AttributedString(markdown:)`, needed for Chat's Markdown rendering, doesn't exist at all in the Linux Foundation this toolchain ships (confirmed by a failed trial build, not merely untested) — so that one piece of view code had to live directly in `apps/macos` rather than as a Linux-testable `AIMACore` helper, unlike everything else added this phase. Phase 2.3's Integrations screen was fully verifiable through `AIMACoreTests`, since credential-form logic and view-model state are ordinary Swift/Foundation, not SwiftUI-only APIs.

### iPhone App
- Optimized for quick capture (notes, tasks, voice) and reviewing/approving pending actions on the go.
- Push notifications used for Tier 3 approval requests ("AIMA has a draft reply ready for Client X — review?").

### Web Dashboard
- Read/write access to the same workspaces via browser; useful when away from an Apple device.
- No local storage of sensitive data beyond session-scoped cache.

### Future Apple TV Companion
- Presentation-only surface (e.g., ambient daily briefing, MFS production board on a big screen). Not an input-heavy surface. Deferred until core product is proven — mentioned here only to confirm the shared-SwiftUI approach won't need rearchitecting to support it later.

## 3. Backend Architecture

### API Layer
- A single backend service exposing a versioned API (REST for CRUD/workflow operations, WebSocket or SSE for streaming AI responses and real-time notifications).
- API is organized around **workspace-scoped resources**: every request carries a workspace context, and the API layer resolves data access accordingly (see Section 6).
- The API layer is the only component allowed to talk to the database, storage, and the AI orchestration layer. Clients never call the LLM provider or database directly.

### Authentication
- Single-user system in early versions — authentication exists primarily to secure the account against unauthorized device/browser access, not to manage multiple tenants.
- Use a managed auth provider (Section 8) rather than building auth from scratch — solo developer time is better spent on AIMA's actual value.
- Session-based auth for clients (short-lived access tokens + refresh tokens), device-level revocation supported (e.g., "sign out this device") from day one, since this is a security-relevant control that's cheap to add early and expensive to retrofit.

### Database
- One primary relational database, with a `workspace_id` (or equivalent partition key) present on every workspace-scoped table, enforced at the schema and query level — not just filtered in application code (Section 6 details isolation).
- Core entities: Users, Workspaces, Conversations/Messages, Memory Records, Knowledge Documents (`documents`/`document_chunks` — Phase 1.5, see §4), Tasks/Projects, Leads/Clients (RCS), Story/Character Records (MFS), Action Log entries, Permission Tier assignments.

### Storage
- Separate object storage for unstructured/binary content: documents, images, proposal PDFs, creative assets, exported files.
- Storage objects reference their owning workspace and are subject to the same isolation rules as database rows.

### Task Foundation (Phase 1.6)
A minimal, workspace-scoped task model — `backend/src/tasks/taskService.ts` over the `tasks` table (created in `0001_init.sql`, given a `priority` column in `database/migrations/0005_task_priority.sql`). Fields: `id`, `workspaceId`, `title`, `description`, `status` (`todo`/`in_progress`/`done`/`cancelled`), `priority` (`low`/`medium`/`high`, defaults to `medium`), `dueDate`, `createdAt`/`updatedAt`. Create/list/get/update/delete, all workspace-isolated. Deliberately no assignment, subtasks, labels, or advanced querying yet — this phase built the data foundation the `create_task` intent (Phase 1.4) already anticipated, not a full task-management feature (docs/decisions/0006-assistant-core-orchestration.md).

### System Health Layer (Phase 1.6)
`backend/src/health/healthService.ts`, exposed at `GET /health`, reports whether each major subsystem is reachable: database, memory (`memory_records` query), knowledge (`document_chunks` query), and AI provider. The AI provider check reports **configuration only** (which provider is selected, e.g. `mock`/`claude`) rather than making a real completion call on every poll — a network ping would cost tokens/latency on a health check that might run every few seconds, a bad tradeoff for an MVP. Each check runs independently, so one failing subsystem is reported without masking the others.

### Action Preparation Layer (Phase 1.7)
A minimal, workspace-scoped model for held content a user reviews before anything is sent — `backend/src/drafts/draftService.ts` over the `drafts` table (`database/migrations/0007_drafts.sql`). Fields: `id`, `workspaceId`, `type` (`email`/`proposal`/`client_response`/`report`), `title`, `content`, `metadata` (JSONB), `createdAt`/`updatedAt`. Create/list/get/update/delete, all workspace-isolated, mirroring `TaskService`'s shape. Creation is gated per `type` by its own capability (`draft_email`, `draft_proposal`, `draft_client_response`, `draft_report` — all Tier 2/prepare); update/delete are plain scoped writes, the same foundation-scope decision Task Foundation made in Phase 1.6. Deliberately does not send, execute, or otherwise act on a draft's content — nothing in this phase wires a draft to an actual send action (docs/decisions/0007-intent-and-approval-workflows.md).

### User Profile System (Phase 1.8)
`backend/src/users/userService.ts` over the `users` table, extended by `database/migrations/0008_user_profile_and_workspace_config.sql` with `preferences` (JSONB, an account-level settings blob — e.g. future UI/notification settings, distinct from the Preference Memory Layer below), `communication_style`, and `default_workspace_id` (nullable, FK to `workspaces`, validated to belong to the same user). Single-user MVP (docs/PRODUCT_BIBLE.md) — no signup/auth flow, so `createUser` exists for seeding only; `GET/PATCH /api/users/:id` (`backend/src/routes/users.ts`) read and update an existing profile.

### Workspace Configuration System (Phase 1.8)
`backend/src/workspaces/workspaceService.ts` — the first application service to own the `workspaces` table, which before this phase was only ever seeded directly via SQL. `slug` remains the fixed identity (Personal/RCS/MFS/Development, docs/PRODUCT_BIBLE.md §1, unchanged); `database/migrations/0008_user_profile_and_workspace_config.sql` adds `type` (`personal`/`business`/`creative`/`development` — a generic behavioral category independent of `slug`), `instructions` (free text), `assistant_behavior` (JSONB structured toggles), `metadata` (JSONB catch-all), and `updated_at`. `type` is nullable at the database level: `WorkspaceService` always resolves and stores it explicitly for workspaces created through it (defaulting via `WORKSPACE_TYPE_BY_SLUG` — personal→personal, rcs→business, mfs→creative, development→development), but a NULL falls back to that same slug-based default in application code, so every pre-existing row and test helper that inserts a bare `(user_id, slug, name)` keeps working unchanged. `POST/GET/PATCH /api/workspaces[/:id]` and `GET /api/users/:id/workspaces` (`backend/src/routes/workspaces.ts`) are deliberately ungated — configuring one of the four fixed workspace kinds is an infrastructure/setup operation, not a conversational capability (docs/decisions/0008-user-identity-and-workspace-intelligence.md).

### Preference Memory Layer (Phase 1.8)
`backend/src/preferences/preferenceService.ts` over a new `preferences` table (`database/migrations/0009_preferences.sql`), structured and categorized (`writing_style`/`response_preferences`/`workflow_preferences`/`project_rules`) — kept separate from freeform `memory_records` because these are keyed settings ("writing_style.tone = formal"), not durable facts. `setPreference` is an upsert on `(workspace_id, category, key)`, gated by a new `set_preference` capability (Tier 2/prepare); `listPreferences`/`getPreference` are ungated reads; `deletePreference` is a plain scoped write. Exposed at `PUT/GET /api/workspaces/:id/preferences` and `DELETE /api/workspaces/:id/preferences/:preferenceId`.

### External Integrations Foundation (Phase 2.3)
`backend/src/integrations/` — a workspace's connection to one of three fixed, read-only providers (Gmail, GitHub, Calendar), built the same way every other cross-cutting concern in this codebase is: a provider abstraction (`IntegrationConnector`, mirroring `ai-engine`'s `AIProvider`/`EmbeddingProvider`) plus a registry (`IntegrationRegistry`, mirroring `CapabilityRegistry`) describing each provider's display metadata, required credential fields, and which capability gates its read/write access. `IntegrationService` owns `connect`/`disconnect`/`rotate`/`listForWorkspace` over `workspace_integrations` (`database/migrations/0011_integrations.sql`), validating credentials against the registry's required fields and calling the connector's `testConnection` before ever storing anything. Credentials are encrypted at rest via `CredentialEncryptor` (AES-256-GCM, keyed by `CREDENTIAL_ENCRYPTION_KEY`) in a separate `integration_credentials` table, deleted outright on disconnect rather than merely disabled. The three connectors shipped this phase (`StubGmailConnector`/`StubGitHubConnector`/`StubCalendarConnector`) are deterministic stubs, not live network clients — real OAuth app registration and consent flows are outside this environment's scope, so this phase ships the framework, credential layer, and UI, not a working data pipeline (docs/decisions/0011-external-integrations-foundation.md). Four new capabilities gate actually using a connection once it exists —`read_email`, `draft_gmail_email`, `read_repositories`, `read_calendar` — all Tier 3 (execute_with_approval) and tier-locked, per §5's reasoning for anything touching a connected external account; consistent with `send_email`'s long-standing state, none has a caller yet, since no route reads data through a connector this phase.

### Workflow Orchestration Foundation (Phase 2.4)
`backend/src/workflows/` — multi-step, approval-gated sequences built on top of the existing capability/approval machinery rather than a parallel one, following the same registry-plus-execution-layer split as `IntegrationRegistry`/`IntegrationService` (Phase 2.3): a `WorkflowRegistry` (mirroring `CapabilityRegistry`) holds four built-in `WorkflowDefinition`s (`draft_email_reply`, `create_github_issue_draft`, `summarize_unread_email`, `daily_workspace_briefing`), each exactly two steps, and a `WorkflowService` owns `create`/`executeNextStep`/`pause`/`resume`/`cancel`/`listRuns` over two new tables (`workflow_runs`, `workflow_step_runs`, `database/migrations/0012_workflows.sql`). The defining structural decision: `executeNextStep` advances **exactly one step per call**, never looping to completion — this is what makes "pause" a real operation and what enforces "no automatic execution" structurally, not by convention. A step gated by a capability that requires approval (only `read_email`, Tier 3, in this phase's four workflows) pauses the run at `awaiting_approval` and creates a genuine `pending_approvals` row via the existing `ApprovalEngine`; the step's real effect (its `WorkflowHandler.executeStep`) is never invoked until `resume()` re-checks that the approval was actually granted. The other three workflows' external-facing steps (`draft_email`, `draft_github_issue`) are Tier 2/prepare and auto-execute, since they only ever write to AIMA's own `drafts` table — `create_github_issue_draft` needed a new `github_issue` draft type and `draft_github_issue` capability for exactly this reason, since the read-only GitHub integration (Phase 2.3) has no write capability by design. A new `WorkflowIntentMatcher` (rule-based, mirroring `ai-engine`'s `RuleBasedIntentClassifier` but scoped to workflows) is wired into `ConversationService.sendMessage`, attaching an advisory `WorkflowSuggestion` to the response when the message matches a built-in workflow's trigger phrases — it never itself creates or executes a `WorkflowRun`. See `docs/decisions/0012-workflow-orchestration-foundation.md`.

### Productivity Intelligence (Phase 2.5)
`backend/src/insights/` — read-only analysis composed entirely from existing services, adding no new persistence: a `BriefingService` (Daily Briefing — workspace summary, pending approvals, active workflow runs, priority tasks, recent activity, all fetched fresh on every call, distinct from the stateful Phase 2.4 `daily_workspace_briefing` *workflow*), a `TaskIntelligenceService` (suggested priorities, due-soon/overdue detection, related-task grouping — deterministic, `taskAnalysis.ts`, no AI call, mirroring `WorkflowIntentMatcher`'s "pure function over what's already known" precedent), a `ConversationIntelligenceService` (summary and suggested follow-ups via the `AIProvider`, plus recent context and related memories via `MemoryService.getWorkspaceContext` — the one piece of this phase that genuinely needs the AI, since "what to ask next" has no deterministic substitute), and a `WorkspaceInsightsService` (aggregate activity/workflow/approval/task-completion metrics, counts only). Every route is a plain `GET` — no capability, no `ActionLogger.log`, no `pending_approvals` row — matching the phase's own rule that this is read-only intelligence, not a new action surface. `ActionLogger` gained its first read methods (`list`/`countByOutcome`) for this phase, ordered by a new `sequence` column (`database/migrations/0013_action_log_sequence.sql`) — the fifth table to need the same frozen-`now()` fix as `messages`/`pending_approvals`/`conversations`/`workflow_runs`. See `docs/decisions/0013-productivity-intelligence.md`.

### Action Execution Foundation (Phase 2.6)
`backend/src/execution/` — the secure execution layer for external actions, built entirely on the existing Approval Engine, Workflow Engine, Integration Framework, and Capability Registry rather than a parallel system, following the same registry-plus-service split as `IntegrationRegistry`/`IntegrationService` (Phase 2.3) and `WorkflowRegistry`/`WorkflowService` (Phase 2.4): an `ActionExecutor` interface (mirroring `WorkflowHandler`/`IntegrationConnector`) and an `ExecutionRegistry` (`Map`-based, seeded with the four built-in executors), plus an `ExecutionService` owning `preview`/`createExecutionRequest`/`execute`/`listHistory`/`getExecution` over a new `executions` table (`database/migrations/0014_executions.sql`). The defining structural decision, directly mirroring Phase 2.4's: `execute` advances **at most one attempt per call** and is idempotent on a terminal `succeeded`/`failed` record — a retry never re-contacts the provider — and always re-checks approval fresh via `ApprovalEngine.get`, never trusting the state captured at creation time. `createExecutionRequest` persists and evaluates approval but never contacts a provider, rejecting up front (before creating anything) if the integration isn't connected — enforcing "reject unauthorized execution before contacting providers" structurally, the same way Phase 2.4 enforces "no automatic execution." Four executors ship this phase: `GmailSendEmailExecutor`/`GmailSaveDraftExecutor` are the first real callers of the `send_email` (Phase 1.4) and `draft_gmail_email` (Phase 2.3) capabilities, and `GitHubCreateIssueExecutor`/`GitHubCreatePullRequestExecutor` back two new Tier 3 tier-locked capabilities (`create_github_issue`, `create_github_pull_request`) — a deliberate, explicitly-requested reversal of Phase 2.3/2.4's "GitHub integration is read-only by design," documented in `docs/decisions/0014-action-execution-foundation.md`. All four executors call into `StubGmailConnector`/`StubGitHubConnector`'s new write methods, still deterministic stubs rather than live network clients, consistent with Phase 2.3's connector precedent. A new `ExecutionIntentMatcher` (rule-based, mirroring `WorkflowIntentMatcher`) is wired into `ConversationService.sendMessage`, attaching an advisory `ExecutionSuggestion` to the response when the message matches a built-in action's trigger phrases — it never itself creates or runs an execution, and is deliberately allowed to co-fire alongside a `WorkflowSuggestion` on the same message, since both stay purely advisory. See `docs/decisions/0014-action-execution-foundation.md`.

### Live Integration Providers (Phase 2.7)
`backend/src/oauth/` and updated `backend/src/integrations/connectors/` — replaces Phase 2.3's deterministic stub connectors with real API clients, without redesigning the Integration Framework or Action Execution Foundation around them. A new `OAuthProvider` interface (`GoogleOAuthProvider`, shared by `gmail`/`calendar` since both are Google APIs and differ only by scope/redirect URI; `GitHubOAuthProvider`) implements the authorization-code flow, and `OAuthService` orchestrates it: `startAuthorization` issues a short-lived, in-memory CSRF `state` and returns the provider's authorization URL; `completeAuthorization` (invoked by the one genuinely provider-driven route, `GET /api/oauth/:provider/callback`) verifies that state, exchanges the code, and connects through the *existing*, unmodified `IntegrationService.connect` — reusing Phase 2.3's encrypted credential storage exactly as-is. Token refresh is transparent: `IntegrationService.getDecryptedCredentials` checks the stored expiry and, if a registered `OAuthProvider` and refresh token both exist, refreshes and persists before returning — so `ExecutionService` and every workflow handler needed zero changes to start working against tokens that actually expire and rotate. A new non-secret `workspace_integrations.token_expires_at` column (`database/migrations/0015_oauth_token_expiry.sql`) lets a client see when a connection's token expires without the backend ever exposing the token itself. `GoogleGmailConnector`/`LiveGitHubConnector`/`GoogleCalendarConnector` replace the stub connectors in production wiring, calling their real REST APIs directly via `fetch` (mirroring `ai-engine`'s `OpenAIEmbeddingProvider` precedent) with an injectable `fetchFn` so every test runs against a fake, never a live network call. Calendar gains its first three write actions (`create_calendar_event`/`update_calendar_event`/`delete_calendar_event`, Tier 3 tier-locked, with matching `ActionExecutor`s) — the same treatment Phase 2.6 gave GitHub's first two writes. See `docs/decisions/0015-live-integration-providers.md`.

### Security
- All traffic over TLS. All stored sensitive data encrypted at rest.
- Secrets (API keys, provider credentials) held in a managed secrets store, never in client code or repo.
- Detailed in Section 9.

## 4. AI Architecture

### AI Model Communication
- The backend's AI orchestration layer is the sole caller of the LLM provider. It assembles: system instructions (AIMA's identity, active workspace rules, permission tier context), retrieved memory/knowledge (below), and the user's current input, then streams the response back through the API layer to the client.
- Model-agnostic interface internally (a thin adapter around the provider call) so the underlying model/provider can be upgraded without touching the rest of the system.
- Implemented end-to-end as `backend/src/conversation/conversationService.ts` (persistence, workspace isolation) delegating to `backend/src/core/aimaCoreService.ts` (the actual orchestration — Phase 1.6, see below) for the pipeline described in §7:
  `User Input → Workspace Context → Memory Retrieval → Context Assembly → AI Provider → Response → Conversation Storage`.
  Responses still stream through the API layer at the HTTP level as a single JSON response for now — token-level streaming to the client is a UI-sprint concern, not yet built.

### Assistant Core Orchestration Layer (Phase 1.6)
The coordinator connecting every AIMA capability for a single request, split into three pieces so each is independently testable and reusable:

- **`AimaCoreService`** (`backend/src/core/aimaCoreService.ts`) — given a workspace, a query, and pre-fetched conversation history, it gathers context (via `ContextManager`), detects intent (via `IntentEngine`), loads the workspace's own configuration (via `WorkspaceService`, Phase 1.8), builds the effective assistant profile, assembles the system prompt, and calls the AI provider. It deliberately owns none of the isolation checks or persistence that guard it — `ConversationService` still validates that a conversation belongs to its workspace and saves messages before/after calling it. This split means `AimaCoreService` can be reused by any future caller that needs a workspace-aware AI response without a persisted conversation (e.g., a future one-off "ask AIMA" endpoint), without duplicating the pipeline. **(Phase 1.7)** it also resolves the detected intent's mapped capability and calls `ApprovalEngine.evaluate` with the intent's extracted parameters as the payload — turning `IntentEngine`'s advisory "would this need approval" flag into a real, trackable `pending_approvals` row whenever the capability is actually Tier 3 (see Intent & Approval Engine below).
- **`ContextManager`** (`backend/src/core/contextManager.ts`) — the Unified Context Manager: combines conversation history (accepted pre-fetched — loading/capping messages is `ConversationService`'s persistence concern, not a context-assembly concern), workspace memory, document context, and **(Phase 1.8)** workspace preferences into one `UnifiedContext`, with independently configurable `memoryLimit`/`documentLimit` (preferences are never limit-capped — small and curated by design). This is the same Promise.all-based retrieval `ConversationService` used to do inline, extracted so it's testable without a full conversation pipeline (`docs/decisions/0006-assistant-core-orchestration.md`).
- **Assistant Behavior Layer** (`backend/src/core/assistantProfiles.ts`) — a static `AssistantProfile` per workspace slug (`name`, `description`, `responseInstructions`), unchanged since Phase 1.6 and still the baseline every workspace of that slug gets. **(Phase 1.8)** `buildEffectiveProfile(workspace)` composes this static default with a workspace's own DB-backed `instructions`/`assistantBehavior` (Workspace Configuration System, §3) — the workspace's configuration only ever *adds* to the static baseline, never replaces it, so `getAssistantProfile(workspaceSlug)` alone still works everywhere a bare slug (not a full `Workspace` row) is available.

### Memory System
Implemented in the Intelligence Sprint as `memory_records` (database/migrations/0002_memory_scopes.sql) plus `backend/src/memory/memoryService.ts`. Four scopes cover the categories from docs/PRODUCT_BIBLE.md:

- **`workspace`** — general durable knowledge about a workspace (the default/catch-all).
- **`user`** — a durable personal-preference fact (e.g., "always draft proposals in a formal tone"). Recorded **within** a workspace, not globally across workspaces — see the design note below.
- **`conversation`** — tied to a specific `conversation_id`; required for this scope.
- **`project`** — tied to a `project_key` tag (a lightweight string, not a full `projects` table, to avoid a relational entity the MVP doesn't need yet); required for this scope.

**Design note (see `docs/decisions/0002-memory-and-embeddings.md`):** every memory row still carries a required `workspace_id` — workspace isolation (§6) is never relaxed, even for "user" scope. A memory scoped `user` is a durable fact recorded *inside* a given workspace, not a cross-workspace global. True cross-workspace recall remains the explicit, logged bridging described in docs/PRODUCT_BIBLE.md §6, and is not implemented by the memory system itself.

**Short-term (in-session conversation history)** is implemented as the `conversations`/`messages` tables, written by `ConversationService`. Message ordering uses a monotonic `sequence` column (`database/migrations/0003_message_sequence.sql`) rather than `created_at` alone — under READ COMMITTED, `now()` is frozen at transaction start, so two messages saved in the same transaction (a user turn and its assistant reply) can share an identical timestamp, making timestamp-only ordering unreliable.

### Context Management
Split between `ConversationService` (persistence) and the Assistant Core Orchestration Layer (above), which together run this for every turn:

1. `ConversationService` confirms the conversation belongs to the given workspace (the isolation checkpoint — see §6) and saves the user's message.
2. `ConversationService` loads recent conversation history (capped at `historyLimit`, default 10 messages — a persistence-layer context limit) and hands it to `AimaCoreService.handleRequest`.
3. `AimaCoreService` calls `ContextManager.gatherContext`, which retrieves relevant workspace memory (`MemoryService.getWorkspaceContext`, capped at `memoryLimit`, default 5), document chunks (`DocumentService.search`, capped at `documentLimit`, default 5), and **(Phase 1.8)** all structured preferences for the workspace (`PreferenceService.listPreferences`, uncapped) in parallel — memory/document **context limits** applied by count rather than token counting, to keep this MVP-simple. In parallel with this, `AimaCoreService` also loads the workspace's own configuration via `WorkspaceService.getWorkspace`.
4. `AimaCoreService` builds the effective assistant profile (`buildEffectiveProfile`, §4 Assistant Behavior Layer) and calls `contextAssembly.ts#buildSystemPrompt`, which assembles: AIMA's identity → the effective profile's workspace description and response instructions → workspace preferences → retrieved memory → retrieved documentation (each snippet truncated to 500 characters so one long item can't dominate the prompt).
5. `AimaCoreService` calls the AI provider with the system prompt and capped history — in parallel, it resolves the detected intent's mapped capability (if any) and calls `ApprovalEngine.evaluate` with it, producing a real `approvalDecision` alongside the completion, gathered context, and detected intent, all returned to `ConversationService`.
6. `ConversationService` saves the assistant's reply and logs the generation (`generate_ai_response` capability, Tier 1/suggest, logged for transparency but not gated — see §5), including the detected intent and approval decision in the log payload.

Context retrieval is workspace-scoped by construction: `MemoryService.search`/`DocumentService.search` always filter by `workspace_id`, so it is not possible for MFS character memory to be returned for an RCS query unless the caller explicitly bridges workspaces (Product Bible §6) — which nothing in the current codebase does yet. See `docs/decisions/0003-conversation-pipeline.md` for the original context-limit/logging-tier rationale and `docs/decisions/0006-assistant-core-orchestration.md` for the orchestration-layer split.

### Knowledge Retrieval
- Retrieval uses pgvector's HNSW index (`idx_memory_records_embedding`, cosine distance) over the `embedding` column — similarity search happens in Postgres, not in application code.
- Embeddings are produced through the same provider-abstraction pattern as chat completions: `ai-engine/src/embeddings/` defines an `EmbeddingProvider` interface with `MockEmbeddingProvider` (deterministic hashed bag-of-words, no network — the default) and `OpenAIEmbeddingProvider` (real embeddings via `text-embedding-3-small`, called with `fetch` rather than adding the full `openai` SDK dependency). Selected at runtime via `EMBEDDING_PROVIDER`, mirroring `AI_PROVIDER`.
- `MemoryService.search` returns ranked results (`1 - cosine_distance` as `score`), optionally filtered by scope, `conversationId`, or `projectKey` — this is the RAG "retrieve relevant chunks" step, now actually injected into the prompt (see Context Management above).

### Knowledge Ingestion (Phase 1.5)
Implemented as `backend/src/knowledge/` — a separate module and pair of tables (`documents`, `document_chunks`; `database/migrations/0004_documents.sql`) from memory, since ingested reference material has a different lifecycle (import, re-index, delete) than assistant-curated memory (docs/decisions/0005-knowledge-ingestion.md):

- **Parsing:** `DocumentParser` interface (mirroring `AIProvider`/`EmbeddingProvider`/`IntentClassifier`) with real `markdown`/`plaintext` implementations and a `pdf` stub that fails clearly (`DocumentFormatNotImplementedError`) — the format is recognized end-to-end (API validation, storage) without a PDF parsing dependency before one is needed.
- **Chunking:** `chunking.ts#chunkDocument` — a pure, deterministic function. Paragraphs (blank-line-separated) are tagged with their nearest preceding Markdown heading as `section`, then packed greedily up to a character limit (`maxChunkChars`, default 1000); a single paragraph longer than the limit is hard-split at character boundaries so no chunk ever exceeds it. Same input always produces the same chunks — required for embeddings and predictable re-indexing.
- **Metadata:** each `documents` row stores `workspace_id`, `title`, `format`, `source`, `tags` (`text[]`), `version`, and `raw_content` (the canonical parsed text, kept so re-indexing doesn't require re-supplying content); `imported_at`/`updated_at` timestamps. Each `document_chunks` row carries `document_id`, a denormalized `workspace_id` (so isolation-sensitive queries never need a join), `chunk_index`, `section`, `content`, and `embedding`.
- **Embedding:** `DocumentService` embeds every chunk via the same `EmbeddingProvider` used by `MemoryService` — no new provider abstraction was needed.
- **Retrieval:** `DocumentService.search` mirrors `MemoryService.search`'s shape (ranked by cosine similarity, workspace-scoped). `ConversationService.sendMessage` now retrieves both memory and document chunks in parallel (each capped independently — a `documentLimit`, default 5, alongside the existing `memoryLimit`/`historyLimit`) and `contextAssembly.ts#buildSystemPrompt` renders them as two separate, clearly labeled sections rather than one merged ranked list, since they carry different metadata (scope vs. document/section) and merging would need an arbitrary cross-type ranking rule this MVP doesn't need.
- **Lifecycle API:** `backend/src/routes/documents.ts` — import, list, search, get, re-index, delete, all workspace-scoped. Import/reindex/delete are routed through the `PermissionEngine`/`ActionLogger` under three new Tier 2 capabilities (`import_document`, `reindex_document`, `delete_document`) — internal, reversible actions, consistent with `create_memory`'s classification.

### Intent & Approval Engine
Built in Phase 1.4 and expanded into full workflows in Phase 1.7 (docs/decisions/0007-intent-and-approval-workflows.md). Two deliberately separate components, plus a third that connects them:

- **Intent Engine** (`ai-engine/src/intent/` + `backend/src/intent/`): classifies the user's message into one of a fixed set of structured intents — `chat`, `remember`, `create_task`, `draft_email`, `draft_proposal`, `summarize`, `search_memory`, `search_documents`, `unknown` — via `IntentClassifier` (an abstraction mirroring `AIProvider`/`EmbeddingProvider`; the current implementation, `RuleBasedIntentClassifier`, is pattern-matching with no AI call). Classification also does best-effort **parameter extraction**: e.g. `create_task` → `{ title }`, `draft_email`/`draft_proposal` → `{ topic }`, `search_memory`/`search_documents` → `{ query }` — the text following the matched trigger phrase, cleaned of leading connectors and trailing punctuation. No NLP; it's "the rest of the sentence," good enough for an MVP where the AI provider does the real reasoning. `backend/src/intent/intentEngine.ts#IntentEngine` then maps the intent to the capability that would handle it (`intentCapabilityMap.ts`) and asks the **Permission Engine** what tier that capability currently resolves to. The result — intent, confidence, extracted parameters, an advisory `ApprovalRequirement` (`no_approval_needed`/`approval_required`), and a human-readable suggested next action — is attached to every conversation response as metadata. **It never writes to the database and never executes anything**; it only reports what *would* happen (docs/decisions/0004-intent-and-approval-engine.md).
- **Approval Engine** (`backend/src/approval/approvalEngine.ts`): the DB-backed half of Tier 3 handling, over the `pending_approvals` table. Its lifecycle (`ApprovalStatus`) is `pending` → `approved` | `rejected`, plus a fourth, **derived** state: `expired`. `expires_at` is written once at creation (`database/migrations/0006_approval_lifecycle.sql`, default 24 hours); "expired" is never persisted as its own status — `ApprovalEngine` computes it at read time (a still-`pending` row past its `expires_at`), so no background job is needed to flip it, and `approve()`/`reject()` on an expired row throw `PendingApprovalExpiredError` rather than silently resolving it. `evaluate()` returns `no_approval_needed` immediately for Tier 1/2/4 capabilities (no DB write); for a Tier 3 capability it creates a `pending_approvals` row and returns `pending` with its id. `list()`/`get()` retrieve approvals (optionally filtered by effective status); `approve()`/`reject()` resolve a pending one. Every method enforces workspace isolation identically for "doesn't exist" and "belongs to another workspace." Exposed at `GET/POST /api/workspaces/:id/approvals[/:approvalId[/approve|reject]]` (`backend/src/routes/approvals.ts`) — deliberately **no public "create" route**: a pending approval is only ever created as a side effect of `AimaCoreService` (or any future caller) attempting a Tier 3 action through `ApprovalEngine.evaluate`, never from a raw client-supplied `actionType`, so the approval gate can't be bypassed or spoofed from the API.
- **The connection (Phase 1.7):** `AimaCoreService` (§4, Assistant Core Orchestration Layer) is the piece that turns the Intent Engine's advisory flag into a real Approval Engine record — resolving the detected intent's capability and calling `evaluate()` with the intent's extracted parameters as the payload, every conversation turn. None of the 9 initial intents' default-tier capabilities are Tier 3 today (by the Product Bible's own classification they're all internal/reversible), so this path creates zero rows under the shipped defaults — it activates automatically the moment any of those capabilities is promoted to Tier 3 (e.g. via a future per-workspace override), with no further backend changes. This is what makes "approval requirements cannot be bypassed" true in practice, not just in the advisory metadata.

**Response schema:** `ConversationService.sendMessage` returns `{ userMessage, assistantMessage, retrievedMemories, retrievedDocumentChunks, intent: { intent, confidence, parameters, approval, suggestedNextAction }, approvalDecision: { state, pendingApprovalId? } }` — the AI response, what was retrieved from memory and documentation, the detected intent with its extracted parameters, whether it would need approval (advisory), and the real approval lifecycle decision if applicable. (`retrievedDocumentChunks` was added in Phase 1.5; `parameters` and `approvalDecision` in Phase 1.7 — see below.)

A prerequisite fix landed alongside this: `capabilities` (docs/TECHNICAL_ARCHITECTURE.md §5) was an empty table with a `NOT NULL` foreign key from `pending_approvals` — nothing could ever populate it. `backend/src/permissions/syncCapabilities.ts#syncCapabilitiesToDatabase` upserts the in-code registry into that table (by `action_type`) once at backend startup, so the registry remains the single source of truth while the DB gets a stable row to reference.

### Future Multi-Agent Capability
- Not built in the MVP, but the orchestration layer is designed so that a single "AIMA" request can later be decomposed into specialized sub-agents (e.g., a "research agent," a "drafting agent," a "code agent") coordinated by a controller — because context assembly, memory, and permission-checking are already centralized rather than duplicated per client. This is a reason to keep orchestration server-side and centralized now, not a feature to build now.

## 5. Permission Architecture

This section is the technical enforcement of the Product Bible's four-tier system (Suggest / Prepare / Execute with Approval / Automatic Safe). Enforcement lives in the backend's **Permission Engine**, a dedicated component every action-producing code path must pass through.

### Mechanism
1. Every capability in the system is registered with a **declared tier** (Tier 1–4) in a central capability registry — no code path can perform an action without an entry here (Development Rule from Product Bible §9: "No unclassified capabilities").
2. When the AI orchestration layer produces an output that maps to a registered action (e.g., "send this email," "log this task"), it does not execute it — it emits an **intent object**: `{ action_type, tier, payload, workspace, rationale }`.
3. The Permission Engine inspects the intent's tier:
   - **Tier 1 (Suggest):** Rendered to the user as text/UI only. No intent execution path exists — nothing to gate.
   - **Tier 2 (Prepare):** The engine persists the drafted artifact (email draft, proposal, plan) in a "pending review" state, visible to the user. No external or irreversible effect occurs.
   - **Tier 3 (Execute with Approval):** The engine creates a **pending approval record** and blocks execution until the specific user, on the specific client, explicitly confirms that specific instance. Only after confirmation does the engine invoke the actual action (send email, push commit, etc.).
   - **Tier 4 (Automatic Safe):** The engine checks whether this action *category* has been explicitly promoted by the user (a flag on the capability registry entry, user-controlled). If yes, it executes immediately; if the promotion flag is ever off, it behaves as Tier 3.
4. Every Tier 3 and Tier 4 execution writes an entry to the **Action Log** (what, when, why, which workspace, which tier, outcome) before returning success to the user. Logging is not optional and not best-effort — a failed log write blocks the action.
5. Certain action types (external communication, financial actions, deletions) are marked **tier-locked at Tier 3 minimum** in the registry itself — the promotion mechanism structurally cannot move them to Tier 4, per Product Bible §5.

**Implementation status:** the capability registry, `PermissionEngine.evaluate`, and the Action Log have been live since the Foundation Sprint. What was missing until the Intent & Approval Engine phase was (a) a structured way to detect *which* capability a conversational message maps to — the Intent Engine, described in §4 — and (b) the `capabilities` table actually being populated, since `pending_approvals.capability_id` is a `NOT NULL` foreign key to it (`syncCapabilitiesToDatabase`, called once at backend startup). Tier 3's "creates a pending approval record" step is implemented as `ApprovalEngine.evaluate` (§4), and as of Phase 1.7 `AimaCoreService` calls it automatically for every conversation turn (not just when exercised directly in tests) — nothing in the codebase yet calls the "invoke the actual action" half of Tier 3, since no real external-action capability has been built (Integration Sprint scope).

### Why this belongs in the architecture, not the prompt
Relying on the AI model to "remember" to ask for permission is not sufficient — model behavior is probabilistic and prompts can be misinterpreted or, in future multi-agent scenarios, bypassed. The Permission Engine is a deterministic backend gate that runs regardless of what the model outputs, ensuring the Product Bible's guarantees hold even as the AI layer evolves.

## 6. Workspace Architecture

Workspace isolation (Personal, RCS, MFS, Development) is enforced structurally at the data layer, not just filtered in the UI.

- **Partitioning:** Every workspace-scoped table/collection carries a `workspace_id`. All queries issued by the API layer are scoped by the active workspace context derived from the authenticated request — there is no code path that queries "all data" without an explicit, logged cross-workspace exception.
- **Memory and knowledge partitioning:** Long-term memory records and knowledge base documents (Section 4) are tagged by workspace at creation and retrieved only within that workspace's scope by default.
- **Cross-workspace bridging:** When the user explicitly requests it (Product Bible §6, Cross-Workspace Rule 2), the API layer performs an explicit, named cross-workspace query (e.g., `bridge_query(source=MFS, target=RCS, reason=...)`), which is itself logged as an action. This keeps bridging rare, visible, and intentional rather than an accidental default.
- **Workspace-aware permission defaults:** The capability registry (Section 5) can carry different default tiers per workspace for the same action type — e.g., "send email" may default to a stricter confirmation flow in RCS (client-facing, reputational risk) than a similar internal notification in Personal.
- **UI-level reinforcement:** Clients visually distinguish the active workspace (e.g., color/label) so the user always knows which context AIMA is operating in — a usability safeguard on top of the structural backend enforcement.
- **Configuration and preferences (Phase 1.8):** Each workspace now carries its own `type`, `instructions`, `assistant_behavior`, and `metadata` (Workspace Configuration System, §3), plus a structured, categorized set of rows in `preferences` (Preference Memory Layer, §3) — both queried and filtered by `workspace_id` exactly like every other workspace-scoped table, so "which behavior profile applies" and "which preferences influence responses" (§4) never leak across workspaces.

## 7. Data Flow

**User → Application → Backend → AI → Response → User**

1. **User** provides input via a client (typed message, voice, or a structured action like "create task").
2. **Application (client)** authenticates the request, attaches the active workspace context, and sends it to the Backend API. The client performs no business logic — it forwards intent and renders results.
3. **Backend (API layer)** validates the request, resolves workspace scope, assembles relevant context (recent conversation, retrieved memory/knowledge for that workspace — Section 4), and forwards an AI request to the orchestration layer.
4. **AI (orchestration + model)** generates a response, which may include plain text and/or one or more **intents** (proposed actions with a declared tier).
5. Intents are passed to the **Permission Engine** (Section 5):
   - Tier 1/2 intents are attached to the response as suggestions/drafts.
   - Tier 3 intents create a pending approval and are attached to the response as "awaiting your confirmation."
   - Tier 4 intents (if promoted) execute immediately and are logged, then attached to the response as "done — here's what I did."
6. **Response** (text + any drafts/pending approvals/completed-action confirmations) streams back through the Backend API to the **Application**.
7. **User** reads the response, and — for Tier 2/3 items — takes the next action (edit, approve, decline), which re-enters this same flow as a new request.

Every hop in this flow is workspace-scoped and, where an action occurred, logged — so the user (or a future audit view) can always reconstruct "what happened, in what workspace, at what tier, and why."

**Implementation status:** steps 1–3 and 6–7 (client → backend → context assembly → response → client) are fully implemented as `ConversationService.sendMessage` (`backend/src/conversation/`, Conversation Intelligence Sprint). Step 4's "intents" — the AI response containing a structured, tiered action proposal that the Permission Engine parses out of the model's output — are **not yet implemented**: today, a generated response is plain text, logged once as a single `generate_ai_response` action (Tier 1/suggest). Parsing model output into distinct actionable intents (e.g., "draft this email" as a Tier 2 artifact) is Integration Sprint scope, once a real external-action capability exists to route to.

## 8. Technology Recommendations

Recommendations are optimized for **one developer, Apple-first, low operational overhead, and fast path to a working MVP** — while avoiding choices that would require a rewrite to scale later.

| Layer | Recommendation | Why |
|---|---|---|
| macOS + iPhone (+ future tvOS) app | **Swift + SwiftUI**, single shared codebase with platform targets | Native Apple integration (notifications, Shortcuts, iCloud), one codebase for three platforms, strong tooling, no cross-platform framework tax. |
| Web dashboard | **Next.js (React) + TypeScript** | Mature, huge ecosystem, easy to deploy, good fit for a secondary/lighter-weight client; TypeScript keeps it consistent with a Node backend if chosen. |
| Backend API | **Node.js (TypeScript) + Express** — decided for the Foundation Sprint, see [ADR 0001](decisions/0001-backend-stack.md) | Both Node and Python were viable; Node was chosen to share TypeScript types with `ai-engine/` and the future web dashboard. |
| Database | **PostgreSQL** (managed, e.g., Supabase or a managed Postgres host) | Relational integrity for workspace partitioning, mature, supports `pgvector` for embeddings — avoids running a separate vector database in the MVP. |
| Object storage | **S3-compatible storage** (e.g., Supabase Storage, Cloudflare R2, or AWS S3) | Cheap, standard, works with any backend choice. |
| Auth | **Managed auth provider** (e.g., Supabase Auth, Clerk, or Auth0) | Don't build auth in-house; get sessions, device management, and security best practices "for free." |
| AI model provider | **Claude API (Anthropic)** as primary model | Strong reasoning and tool-use for an assistant that must reliably respect permission tiers; use the provider-agnostic adapter (Section 4) to avoid lock-in. |
| Embeddings / retrieval | **`pgvector` inside Postgres** initially; dedicated vector DB only if scale demands it later | Avoids introducing a second database system before it's needed. |
| Hosting / deployment | **Managed platform** (e.g., Fly.io, Render, or Vercel for the web dashboard + API) | Minimal DevOps burden for a solo developer; scale-up path exists without a re-architecture. |
| Notifications (mobile) | **Apple Push Notification service (APNs)**, native | Required for Tier 3 approval prompts on iPhone; standard Apple integration. |
| Background/scheduled jobs | Lightweight job queue (e.g., built-in cron on the hosting platform, or a simple queue like BullMQ if Node) | Needed for things like daily briefings or follow-up reminders; keep it simple until volume demands more. |

**Guiding rule:** every recommendation favors a **managed service over self-hosted infrastructure** wherever the cost is reasonable, because solo-developer time is the scarcest resource in this project — not infrastructure spend.

## 9. Security Considerations

### Authentication
- Managed auth provider (Section 8) with short-lived access tokens and refresh tokens.
- Per-device session tracking with user-visible "signed in devices" list and one-tap revocation.
- All authentication endpoints rate-limited to mitigate credential-stuffing/brute-force attempts, even in a single-user system (defense against a compromised password).

### Data Protection
- Encryption in transit (TLS everywhere) and at rest (managed database/storage encryption).
- Workspace partitioning (Section 6) enforced at the query layer, treated as a security boundary, not just an organizational convenience.
- Regular, automated backups of the database and object storage, with a tested restore process — the user's client data, creative IP, and code context are irreplaceable if lost.

### API Security
- All backend endpoints require authenticated, workspace-scoped requests; no anonymous or cross-workspace-by-default endpoints.
- Input validation and output encoding on every endpoint to prevent injection-class vulnerabilities.
- LLM provider API keys and other secrets held server-side only, in a managed secrets store — never shipped in client binaries or web bundles.
- Rate limiting on AI-invoking endpoints to control cost exposure and abuse risk.

### User Privacy
- No user data (client details, creative IP, code, personal notes) is used to train third-party models beyond what the LLM provider's data-use terms allow for API traffic — this must be explicitly verified against the chosen provider's policy before launch.
- Clear, user-visible data boundaries: the user can see what AIMA has stored about them, per workspace, and can delete it.
- The Action Log (Section 5) doubles as a privacy tool: the user can always see what AIMA did with their data and when.

## 10. Development Roadmap

Four sprints, each producing a working, demonstrable increment. Scope is intentionally conservative per sprint — the goal is a real product quickly, not a fully-featured one immediately.

### Foundation Sprint
- Stand up backend (API layer, managed auth, Postgres with workspace partitioning, object storage).
- Build the macOS/iPhone shared SwiftUI client shell: login, workspace switcher, basic chat interface.
- Implement Tier 1 (Suggest) and Tier 2 (Prepare) only — no external actions yet.
- Basic conversation flow: user message → AI response, scoped to a workspace.
- **Exit criteria:** User can log in, pick a workspace, chat with AIMA, and receive workspace-appropriate responses and drafts.

### Intelligence Sprint
- Build long-term memory storage and retrieval (Section 4), scoped per workspace. ✅ Done — `memory_records` scope model, `MemoryService.createMemory`/`search`/`getWorkspaceContext`, pgvector HNSW ranking, workspace-isolated by construction.
- Build project knowledge base ingestion + retrieval (embeddings via `pgvector`). ✅ Done as the `project` memory scope (`project_key` tag) — a full document-ingestion pipeline (e.g., chunking uploaded files) is not yet built; today's "knowledge" is whatever is explicitly stored as a memory record via the API.
- Improve context assembly so responses reflect real memory/history, not just the current conversation. ⏳ Not done — `getWorkspaceContext` provides the ranked retrieval; wiring its output into an actual chat request's system prompt is Integration Sprint scope (no chat pipeline exists yet to assemble into).
- **Exit criteria met:** AIMA can store and retrieve relevant memory/knowledge per workspace, ranked by relevance, with permission enforcement and workspace isolation intact. Retrieval is not yet connected to a live conversation — that requires the Integration Sprint's chat pipeline.

### Daily Assistant Interface (Phase 2.2)
Deepened the macOS app (§2) from a foundation into something usable day to day, without adding any automation execution. Chat gained Markdown-rendered responses and an inline approval card (approve/reject a real, DB-backed approval without leaving the conversation) alongside the existing advisory intent banner. Two screens were added: Tasks (every workspace task, filterable by status, with a color-coded priority indicator) and Approvals (a full, filterable list-plus-detail view, versus the Dashboard's pending-only quick list). `AIMACore` grew to match: `ApprovalsViewModel`, `TasksViewModel`, `APIClient.getApproval` (backed by the `GET /api/workspaces/:id/approvals/:approvalId` route Phase 1.7 already shipped but no client had used yet), and `JSONValue.displayString`. A `MockAPIClient.forceNextMessageToRequireApproval` test hook lets the chat approval card be exercised in tests even though no capability's shipped default triggers a real Tier 3 approval yet (§3's "what's intentionally not built yet"). See `docs/decisions/0010-daily-assistant-interface.md`, including what a Linux-only environment could verify this phase (all of `AIMACore`'s test suite) versus what it structurally could not (`AttributedString(markdown:)` doesn't exist in Linux Foundation at all, so Chat's Markdown rendering lives untested outside Xcode, unlike everything else added this phase).

### External Integrations Foundation (Phase 2.3)
Built the framework a real external integration will eventually plug into, without wiring one up end-to-end yet. `backend/src/integrations/` adds an `IntegrationRegistry` (provider metadata, required credential fields, which capability gates read/write access) and an `IntegrationService` (connect/disconnect/rotate over `workspace_integrations` + encrypted `integration_credentials`, `0011_integrations.sql`) following the same provider-abstraction pattern as `ai-engine`'s `AIProvider`. Credentials are encrypted at rest with AES-256-GCM (`CredentialEncryptor`, keyed by a new required `CREDENTIAL_ENCRYPTION_KEY`). Four new capabilities — `read_email`, `draft_gmail_email`, `read_repositories`, `read_calendar` — are registered Tier 3 and tier-locked, matching the Product Bible's treatment of anything touching a connected external account, but (like `send_email` since Phase 1.4) have no caller yet: this phase ships the framework, credential layer, and macOS Integrations screen (§2), not a working read pipeline. The three connectors (Gmail/GitHub/Calendar) are deterministic stubs rather than live API clients — registering a real OAuth app and completing a consent flow is outside what this environment can do, so the connector *interface* and its credential-validation contract are what's genuinely tested, not a live network call. See `docs/decisions/0011-external-integrations-foundation.md`.

### Workflow Orchestration Foundation (Phase 2.4)
Built a multi-step workflow engine on top of the existing capability/approval machinery — a workflow registry, a one-step-at-a-time execution framework, and four built-in workflows (draft email reply, create GitHub issue draft, summarize unread email, daily workspace briefing) — plus a macOS Workflows screen (start/execute/pause/resume/cancel, step progress, approval checkpoints) and a chat-integrated, advisory workflow-suggestion card. `summarize_unread_email` is the first real caller of Phase 2.3's `read_email` capability and `IntegrationService`, though it remains approval-gated like everything else touching a connected external account. `AIMACore` grew a `WorkflowsViewModel` and seven new `APIClient` methods; `ChatViewModel` gained `lastWorkflowSuggestion`. No workflow step executes without going through the same Tier/Approval machinery every other action does — this phase is additive orchestration, not a new permission model. See `docs/decisions/0012-workflow-orchestration-foundation.md`.

### Productivity Intelligence (Phase 2.5)
Added a read-only analysis layer over everything AIMA already tracks — a Daily Briefing (workspace summary, pending approvals, active workflows, priority tasks, recent activity), Task Intelligence (deterministic suggested priorities, due-soon/overdue detection, related-task grouping), Conversation Intelligence (AI-assisted summary, suggested follow-ups, related memories), and Workspace Insights (activity/workflow/approval/task-completion metrics) — plus a Dashboard that surfaces all four, and an explicit "Summarize Conversation" affordance in Chat. No new capability, no new writes, no automatic execution: every route is a plain `GET` composed from existing services, and Conversation Intelligence is fetched only on explicit user request, never automatically alongside a message. See `docs/decisions/0013-productivity-intelligence.md`.

### Action Execution Foundation (Phase 2.6)
Built the secure execution layer for external actions on top of the existing Approval Engine, Workflow Engine, Integration Framework, and Capability Registry — an `ActionExecutor` registry, an `ExecutionService` (preview → create request → execute, at most one attempt per call, idempotent on a terminal record), four executors (Gmail send/save-draft, GitHub create-issue/create-pull-request), plus a macOS Executions screen (preview, confirmation dialog, history, detail) and a chat-integrated, advisory execution-suggestion card. The two GitHub write executors are a deliberate, explicitly-requested reversal of Phase 2.3/2.4's "GitHub integration is read-only by design," landed via two new Tier 3 tier-locked capabilities rather than a design change to the existing read-only ones. `send_email` (Phase 1.4) and `draft_gmail_email` (Phase 2.3) get their first real callers this phase. Still no autonomous agents, scheduled execution, background workers, automatic retries, streaming execution, or multi-action execution — every execution remains a single, explicit, approval-gated request. See `docs/decisions/0014-action-execution-foundation.md`.

### Live Integration Providers (Phase 2.7)
Replaced the Phase 2.3 stub connectors with real Gmail/GitHub/Calendar API clients and a full OAuth 2.0 framework (authorization flow, token exchange, refresh, secure storage reusing Phase 2.3's encrypted `integration_credentials`, rotation, best-effort disconnect revocation) — without changing the `IntegrationConnector`/`ActionExecutor` interfaces those clients slot into. `OAuthService` completes the connection server-side once a provider redirects back to a fixed backend callback route; the macOS app's only role is opening a browser and refreshing its own status afterward. Calendar gained its first three write actions (create/update/delete event), following the same new-capability-plus-executor pattern Phase 2.6 used for GitHub's first writes. Every live connector and OAuth provider takes an injectable `fetch`, so the backend test suite (451 tests) exercises real request/response shapes against a fake HTTP layer, never a live network call — an actual OAuth app registration and a live end-to-end test against real Google/GitHub servers remains outside what this environment can do. See `docs/decisions/0015-live-integration-providers.md`.

### Production Deployment Foundation (Phase 3.1)
Made the backend production-ready without deploying it anywhere or requiring any real external account. `loadConfig()` (`backend/src/config/env.ts`) gained a typed `NodeEnv` (`development`/`test`/`production`), moved `CREDENTIAL_ENCRYPTION_KEY`'s 32-byte validation into config load (previously only checked inside the encryptor's constructor), and added a production-only check that `PUBLIC_BACKEND_URL` is `https://` — OAuth providers redirect real users there with authorization codes. A new `Logger`/`ErrorReporter` provider-abstraction pair (`backend/src/logging/`, `backend/src/monitoring/`) mirrors `AIProvider`/`OAuthProvider`: `ConsoleLogger` writes redacted (secret-shaped keys replaced with `[REDACTED]`), human-readable text in development and single-line JSON in production; `ConsoleErrorReporter` logs exceptions through it. Both are optional dependencies on `AppDependencies`/`createApp`, defaulting internally, so no existing test file needed updating. `createPool()` gained optional TLS and pool-size options for managed Postgres providers. `HealthService`'s `GET /health` gained a fifth check, `integrations`, reporting which OAuth-backed providers are registered — computed from the real `oauthProviders` map, not a raw env re-check, and (like the AI provider check) deliberately shallow: no live network call. A production Dockerfile, `.dockerignore`, and `.env.production.example` were added, plus `docs/PRODUCTION_SETUP.md` and a security review confirming credential encryption, OAuth token handling, workspace isolation, and permission/approval enforcement are all still sound with nothing new introduced. See `docs/decisions/0016-production-deployment-foundation.md`.

### Voice Assistant Foundation (Phase 3.2)
Built the foundation for voice interaction without any autonomous voice control. `ai-engine/src/voice/` adds `SpeechToTextProvider`/`TextToSpeechProvider` interfaces mirroring `AIProvider`/`EmbeddingProvider` exactly — `MockSpeechToTextProvider`/`MockTextToSpeechProvider` decode/encode plain UTF-8 text as the "audio" payload (no vendor account, no network call), selected via `SPEECH_TO_TEXT_PROVIDER`/`TEXT_TO_SPEECH_PROVIDER` (default `mock`) through a registry following the same pattern. `backend/src/voice/` (`VoiceService`, `database/migrations/0016_voice.sql`) is a thin orchestrator, not a parallel pipeline: `startSession` creates a real, listable conversation via the unmodified `ConversationService.createConversation`; `submitVoiceRequest` transcribes audio, runs the transcript through `ConversationService.sendMessage` unmodified — so context assembly, intent detection, and approval evaluation all apply exactly as they do to typed chat — then synthesizes the reply. No audio is ever persisted, only transcript text and response text (`voice_turns`). `apps/Shared/AIMACore` gained `VoiceSession`/`Transcript`/`VoiceTurn`/`VoiceConfiguration`/`VoiceResponse` models, six new `APIClient` methods, a `MockAPIClient` reimplementation, and `VoiceSessionViewModel` (session lifecycle, transcript history, response-playback state). The macOS app gained a Voice screen with explicit Start/Stop Session controls and a typed-utterance composer standing in for real microphone capture — `AVAudioEngine` integration is later phase's work, since real audio recording code can't be built/verified in a Linux-only environment anyway. No wake word, background listening, or autonomous conversation exists anywhere: every session and every turn requires an explicit user action. See `docs/decisions/0017-voice-assistant-foundation.md`.

### Real Voice Provider Integration (Phase 3.3)
Replaced the mock-only voice provider layer with a real vendor implementation, without changing any of Phase 3.2's safety boundaries. `OpenAISpeechToTextProvider`/`OpenAITextToSpeechProvider` (`ai-engine/src/voice/`) call OpenAI's Whisper transcription and TTS REST endpoints directly via an injectable `fetch` — the same "one endpoint doesn't need a whole SDK" precedent as `OpenAIEmbeddingProvider` and the Phase 2.7 live connectors — with a configurable request timeout (`AbortController`, default 30s) and a `fakeFetch` test double so no test makes a live network call. `SPEECH_TO_TEXT_PROVIDER`/`TEXT_TO_SPEECH_PROVIDER` now accept `"openai"` alongside the still-default `"mock"`, configured via `_API_KEY`/`_MODEL`/`_TIMEOUT_MS` env vars mirroring `EMBEDDING_PROVIDER`'s convention. `VoiceService` wraps any provider failure in a new `VoiceProviderError`, mapped to HTTP 502 with a generic message — a real vendor's raw error body never reaches the client, since it could echo back request-identifying detail. `HealthService` gained a sixth check, `voiceProviders`, reporting the configured provider names — deliberately shallow, no live vendor call, since provider construction already fails fast at startup if a non-mock provider is missing its API key. `apps/Shared/AIMACore`'s `VoiceSessionViewModel` gained `loadProviderStatus()` (reads the existing health check) and `isProviderError` (set on a 502), and the macOS Voice screen now shows the configured provider and a distinct "voice provider unavailable" state. No audio persistence, session-lifecycle, approval-evaluation, or workspace-isolation behavior changed — swapping providers changes only which class implements the existing interfaces. See `docs/decisions/0018-real-voice-provider-integration.md`.

### Integration Sprint
- Build the Permission Engine's remaining piece (Section 5): per-workspace tier overrides (`workspace_capability_settings`) — the capability registry, tier resolution, Action Log, and now the full pending-approval lifecycle all already exist and are in active use.
- Register real OAuth apps with Google and GitHub, deploy the backend at a publicly reachable `PUBLIC_BACKEND_URL`, and run a live end-to-end connect → execute → disconnect cycle against real accounts — the framework, encryption, and refresh logic are all in place (Phase 2.7); only an actual registered app and a reachable deployment are outside this environment's scope.
- Add push notifications (iPhone) for pending approvals.
- Ship the web dashboard as a secondary client against the now-stable API.
- **Exit criteria:** AIMA can prepare and, upon explicit approval, execute at least one real external action against a live provider (not a stub), fully logged and visible to the user.

### Testing Sprint
- Security review pass: verify workspace isolation cannot be bypassed via API, confirm no secrets are reachable from client code, validate rate limiting and auth revocation.
- Permission system audit: exercise every registered capability and confirm it behaves exactly per its declared tier, including the Tier-3-minimum lock on external/irreversible actions.
- Real-world usage testing across all four workspaces with actual RCS/MFS/personal/dev data to surface UX friction and incorrect context bleed.
- Backup/restore drill: confirm database and storage backups actually restore cleanly.
- Fix and harden based on findings; document known limitations honestly rather than hiding them.
- **Exit criteria:** The developer can confidently use AIMA daily across all workspaces, trusting that permission boundaries, workspace isolation, and data durability hold under real use.
