# backend

AIMA's API layer: authentication, workspace routing, the permission engine, intent detection, the approval lifecycle, the conversation pipeline, memory/document retrieval, and the action log (docs/TECHNICAL_ARCHITECTURE.md §3, §4, §5, §6). This is the only component allowed to talk to the database, object storage, and `ai-engine/` — clients never call those directly.

## Structure

- **`src/config/`** — `loadConfig()`: typed, validated environment configuration, extended in Phase 3.1 (docs/decisions/0016-production-deployment-foundation.md) with a closed `NodeEnv` union (`development`/`test`/`production`), a `CREDENTIAL_ENCRYPTION_KEY` byte-length check moved here from the encryptor's constructor, and a production-only requirement that `PUBLIC_BACKEND_URL` be `https://`.
- **`src/logging/`** — the Logging Foundation (Phase 3.1). `types.ts` defines the `Logger` interface (`debug`/`info`/`warn`/`error`), mirroring `AIProvider`'s provider-abstraction pattern. `ConsoleLogger` is the default implementation: human-readable text in development/test, single-line JSON in production. `redact.ts` recursively replaces any field whose key name looks secret-shaped (`token`, `password`, `credential`, `authorization`, etc.) with `[REDACTED]` before it's ever written.
- **`src/monitoring/`** — the Error Monitoring Foundation (Phase 3.1). `types.ts` defines `ErrorReporter` (`captureException`); `ConsoleErrorReporter` logs the exception (message + stack) through an injected `Logger`, so redaction applies automatically. A real hosted error tracker is a drop-in `ErrorReporter` implementation later, no call-site changes.
- **`src/db/`** — Postgres connection pool (`createPool`, extended in Phase 3.1 with optional `{ ssl, maxConnections }` for managed providers), the shared `Queryable` type (`Pool | Client`, so services work identically in production and inside a test transaction), and `vector.ts` (`toVectorLiteral`, shared by `MemoryService`, `DocumentService`, and (Phase 3.6) `EmbeddingService`/`RetrievalService`).
- **`src/types/`** — shared domain types (workspace slugs) and `errors.ts` (`WorkspaceNotFoundError`, shared by every workspace-scoped service).
- **`src/permissions/`** — the capability registry and `PermissionEngine` (docs/TECHNICAL_ARCHITECTURE.md §5), plus `syncCapabilities.ts`, which upserts the registry into the `capabilities` table at startup (required for `pending_approvals`' foreign key).
- **`src/actionLog/`** — writes to the `action_log` table; the audit trail behind every logged action, gated or not. `ActionLogger` gained its first read methods in Phase 2.5 — `list` (newest first, via a `sequence` column, `database/migrations/0013_action_log_sequence.sql`) and `countByOutcome` — for `BriefingService`'s "recent activity" and `WorkspaceInsightsService`'s activity metrics.
- **`src/memory/`** — `MemoryService`: creates, ranks, updates, archives, and deletes memory records (`docs/TECHNICAL_ARCHITECTURE.md` §4), embedding via `ai-engine`'s `EmbeddingProvider` abstraction. Enforces workspace isolation and memory-scope consistency. Extended in Phase 3.4 (docs/decisions/0019-advanced-memory-system.md) with importance/confidence scoring, a `memory_type` lifecycle dimension (`short_term`/`long_term`, orthogonal to `scope`), and `archived_at`/`expires_at`/`last_accessed_at`. `ranking.ts` (`rankMemories`, `computeRelevanceScore`) is a pure function that blends similarity/importance/confidence to re-rank the candidates `search()` narrows via pgvector — no database access, fully unit-testable. `errors.ts` defines `MemoryNotFoundError`.
- **`src/knowledge/`** — `DocumentService`: the document ingestion lifecycle (import, re-index, delete, list, get, ranked search) over `documents`/`document_chunks` (docs/decisions/0005-knowledge-ingestion.md). `chunking.ts` is a pure, deterministic chunker; `parsers/` holds the `DocumentParser` abstraction (Markdown and plaintext real, PDF a stub that fails clearly).
- **`src/intent/`** — `IntentEngine`: composes `ai-engine`'s `IntentClassifier` with the `PermissionEngine` to attach response metadata (intent, confidence, extracted parameters, an advisory `ApprovalRequirement`, suggested next action). Pure and database-free — never creates a pending approval or executes anything (docs/decisions/0004-intent-and-approval-engine.md). `intentCapabilityMap.ts` maps each of the 9 intents to the capability that would handle it (`null` for pure reads like `search_memory`/`search_documents`).
- **`src/approval/`** — `ApprovalEngine`: the DB-backed Tier 3 lifecycle (`evaluate`/`list`/`get`/`approve`/`reject`) over the `pending_approvals` table, with workspace isolation enforced the same way as `ConversationService`. Lifecycle states are `pending`/`approved`/`rejected`/`expired` — the last derived from `expires_at` at read time, never persisted (docs/decisions/0007-intent-and-approval-workflows.md).
- **`src/core/`** — the Assistant Core Orchestration Layer (Phase 1.6, docs/decisions/0006-assistant-core-orchestration.md). `aimaCoreService.ts` (`AimaCoreService`) is the coordinator: gather context, detect intent, resolve the intent's mapped capability and call `ApprovalEngine.evaluate` with its extracted parameters (Phase 1.7), load the workspace's own configuration via `WorkspaceService` and build the effective assistant profile (Phase 1.8), build the system prompt, call the AI provider, return a structured response — takes conversation history as a plain array, with no knowledge of `conversations`/`messages` tables. `contextManager.ts` (`ContextManager`) combines memory, document, (pass-through) history, and workspace preference context (Phase 1.8) with configurable `memoryLimit`/`documentLimit`. `assistantProfiles.ts` defines the static per-slug `AssistantProfile`s (Personal, Roman Creative Studio, Mythic Forge Studios, Development) plus `buildEffectiveProfile(workspace)`, which composes that static default with a workspace's own DB-backed `instructions`/`assistantBehavior` (Phase 1.8) — additive, never a replacement. `contextAssembly.ts` (moved here from `conversation/`) builds the system prompt from an `AssistantProfile` plus memory/document/preference context. `types.ts` defines `UnifiedContext`/`ContextLimits`.
- **`src/conversation/`** — `ConversationService`: owns conversation/message persistence and workspace isolation only. `sendMessage` validates the conversation, saves the user's message, bumps the conversation's `sequence` via `touchConversation()` (Phase 2.1, `database/migrations/0010_conversation_sequence.sql`), loads history, delegates context-gathering/intent/approval/AI-calling to `AimaCoreService.handleRequest`, then saves the assistant's reply and logs the action (including the detected intent and real approval decision). As of Phase 3.6, it also computes `retrievedContext` via an optional `retrievalService: RetrievalService` dependency and attaches it to `SendMessageResult` as pure advisory metadata (`null` when no `RetrievalService` is configured) — never wired into `AimaCoreService`/`ContextManager`'s actual prompt assembly. `listConversations` (Phase 2.1) returns a workspace's conversations ordered `sequence DESC` — "most recently active first", for the macOS app's Chat screen. Built from a `ConversationServiceDependencies` object (not positional arguments — see docs/decisions/0005-knowledge-ingestion.md #5 and 0006 #1). `errors.ts` defines `ConversationNotFoundError` for clean 404 mapping at the route layer.
- **`src/tasks/`** — `TaskService`: the Task Foundation (Phase 1.6, docs/decisions/0006-assistant-core-orchestration.md #4). Workspace-scoped create/list/get/update/delete over the `tasks` table, mirroring `MemoryService`/`DocumentService`'s shape. Only `createTask` is routed through the `PermissionEngine`/`ActionLogger` (reusing the `create_task` capability registered in Phase 1.4); update/delete are plain scoped writes — a deliberate scope cut for a foundation phase.
- **`src/drafts/`** — `DraftService`: the Action Preparation Layer (Phase 1.7, docs/decisions/0007-intent-and-approval-workflows.md #6). Workspace-scoped create/list/get/update/delete over the `drafts` table for held content — `email`/`proposal`/`client_response`/`report` — reviewed before anything is sent. Creation is gated per `type` by its own Tier 2 capability; never sends or executes anything.
- **`src/health/`** — `HealthService` (Phase 1.6): `check()` verifies the database, `memory_records`, and `document_chunks` are queryable, and reports the AI provider's configured name (not a live completion call — see docs/decisions/0006-assistant-core-orchestration.md #5). Extended in Phase 3.1 with a fifth check, `integrations`, reporting which of Gmail/GitHub/Calendar have a registered `OAuthProvider` — computed from the real `oauthProviders` map `index.ts` builds, not a raw env re-check, and (like `aiProvider`) deliberately shallow: no live network call (docs/decisions/0016-production-deployment-foundation.md). Extended again in Phase 3.3 with a sixth check, `voiceProviders`, reporting the configured speech-to-text/text-to-speech provider names — equally shallow, since provider construction already fails fast at startup if a non-mock provider is missing its API key (docs/decisions/0018-real-voice-provider-integration.md).
- **`src/users/`** — `UserService`: the User Profile System (Phase 1.8, docs/decisions/0008-user-identity-and-workspace-intelligence.md). `getUser`/`updateProfile` over the `users` table's `displayName`/`preferences`/`communicationStyle`/`defaultWorkspaceId`; `createUser` exists for seeding only (no signup flow — single-user MVP).
- **`src/workspaces/`** — `WorkspaceService`: the Workspace Configuration System (Phase 1.8). The first application service to own the `workspaces` table (previously seeded only via raw SQL). `createWorkspace`/`getWorkspace`/`listWorkspaces`/`updateWorkspace` over `slug` (still the fixed identity), `type` (a generic category independent of `slug`, defaulting per `WORKSPACE_TYPE_BY_SLUG`), `instructions`, `assistantBehavior`, and `metadata`.
- **`src/preferences/`** — `PreferenceService`: the Preference Memory Layer (Phase 1.8). Structured, categorized (`writing_style`/`response_preferences`/`workflow_preferences`/`project_rules`) key-value settings, workspace-scoped, kept separate from `memory_records`. `setPreference` is an upsert on `(workspace, category, key)`.
- **`src/integrations/`** — the External Integrations Foundation (Phase 2.3, docs/decisions/0011-external-integrations-foundation.md), now backed by live providers (Phase 2.7, docs/decisions/0015-live-integration-providers.md). `registry.ts` (`IntegrationRegistry`) describes the three fixed providers — display metadata, which capability gates read access, and which capabilities gate write access (`writeCapabilities: string[]`, widened in Phase 2.7 to list every write action a provider supports, not just one) — and which credential fields a connector needs. `encryption.ts` (`CredentialEncryptor`/`AesGcmCredentialEncryptor`) encrypts credentials at rest with AES-256-GCM, keyed by `CREDENTIAL_ENCRYPTION_KEY`, unchanged since Phase 2.3. `integrationService.ts` (`IntegrationService`) is the workspace enable/disable and credential layer: `connect`/`disconnect`/`rotate`/`listForWorkspace`, plus `getDecryptedCredentials` — internal-only, never exposed via a route, called by the `summarize_unread_email` workflow (Phase 2.4) and every `ActionExecutor` (Phase 2.6/2.7). As of Phase 2.7, `getDecryptedCredentials` transparently refreshes an expired OAuth token (via an injected, optional `OAuthProvider` per provider) and persists the result before returning, and `disconnect` makes a best-effort token revocation call before deleting stored credentials — both invisible to every existing caller. `connectors/` holds the `IntegrationConnector` provider abstraction; `StubGmailConnector`/`StubGitHubConnector`/`StubCalendarConnector` remain for tests, while production wiring (`index.ts`) uses the real `GoogleGmailConnector`/`LiveGitHubConnector`/`GoogleCalendarConnector` (Phase 2.7) — real REST API calls via an injectable `fetch`, never a live network call in tests (`testUtils/fakeFetch.ts`).
- **`src/oauth/`** — the OAuth Framework (Phase 2.7, docs/decisions/0015-live-integration-providers.md). `types.ts` defines the `OAuthProvider` interface (`getAuthorizationUrl`/`exchangeCode`/`refreshAccessToken`/`revokeToken`) and `OAuthTokenSet`. `googleOAuthProvider.ts` (`GoogleOAuthProvider`) implements Google's authorization-code flow, parameterized by scope so one class serves both `gmail` and `calendar`. `githubOAuthProvider.ts` (`GitHubOAuthProvider`) implements GitHub's, correctly treating `refresh_token`/`expires_in` as optional (classic GitHub OAuth Apps issue non-expiring tokens with neither). `oauthService.ts` (`OAuthService`) orchestrates the flow: `startAuthorization` issues a short-lived, in-memory CSRF `state` and returns the provider's authorization URL; `completeAuthorization` (invoked only by the `GET /api/oauth/:provider/callback` route) verifies that state, exchanges the code, and connects through the unmodified `IntegrationService.connect` — no parallel credential-storage path.
- **`src/workflows/`** — the Workflow Orchestration Foundation (Phase 2.4, docs/decisions/0012-workflow-orchestration-foundation.md). `registry.ts` (`WorkflowRegistry`) holds the four built-in `WorkflowDefinition`s (`draft_email_reply`, `create_github_issue_draft`, `summarize_unread_email`, `daily_workspace_briefing`), each exactly two steps. `handlers/` holds one `WorkflowHandler` per workflow, each composing existing services (`AIProvider`, `DraftService`, `IntegrationService`, `TaskService`, `ApprovalEngine`, `HealthService`) rather than owning any new persistence. `workflowService.ts` (`WorkflowService`) owns `create`/`executeNextStep`/`pause`/`resume`/`cancel`/`listRuns` over `workflow_runs`/`workflow_step_runs` (`database/migrations/0012_workflows.sql`) — `executeNextStep` advances exactly one step per call, and a step gated by a capability requiring approval pauses the run and creates a real `pending_approvals` row via `ApprovalEngine`, never invoking the step's handler until `resume()` confirms approval. `workflowIntentMatcher.ts` (`WorkflowIntentMatcher`) is a pure, rule-based matcher (mirroring `ai-engine`'s `RuleBasedIntentClassifier`) wired into `ConversationService`, attaching an advisory `WorkflowSuggestion` to chat responses — never itself creating or executing a run.
- **`src/insights/`** — Productivity Intelligence (Phase 2.5, docs/decisions/0013-productivity-intelligence.md). Four services, all read-only, all composed from existing services with no new persistence: `briefingService.ts` (`BriefingService.getDailyBriefing`) aggregates a workspace summary, pending approvals, active workflow runs, priority tasks, and recent activity in one synchronous call — distinct from the stateful Phase 2.4 `daily_workspace_briefing` *workflow*. Extended in Phase 3.5 with `recentMemories` (a plain `MemoryService.listMemories` read), `calendarHighlights` (derived from `recentActivity`'s calendar-write entries — never a live Calendar connector call, since `read_calendar` stays Tier 3/tier-locked), and `suggestedNextActions` (top 3 ranked `Suggestion`s from `ProactiveIntelligenceService`) — both new dependencies are optional trailing constructor parameters, so no existing test file needed updating. `taskAnalysis.ts` holds pure, deterministic functions (`rankTasksByPriority`, `findDueSoon`, `findOverdue`, `groupRelatedTasks`) shared by `briefingService.ts`, `taskIntelligenceService.ts` (`TaskIntelligenceService.analyze`), and (Phase 3.5) `patternDetectionService.ts` — no AI call, mirroring `WorkflowIntentMatcher`'s "pure function over what's already known" precedent. `conversationIntelligenceService.ts` (`ConversationIntelligenceService.analyze`) is the one piece that genuinely needs the `AIProvider` — a summary and suggested follow-ups for a conversation's recent turns, plus related memories via `MemoryService.getWorkspaceContext`. `workspaceInsightsService.ts` (`WorkspaceInsightsService.getInsights`) returns aggregate activity/workflow/approval/task-completion counts only, no row-level detail.
- **`src/proactive/`** — the Proactive Intelligence Engine (Phase 3.5, docs/decisions/0020-proactive-intelligence.md). `patternDetectionService.ts` (`PatternDetectionService.detect`) composes `TaskService`/`WorkflowService`/`ApprovalEngine`/`ActionLogger`/`MemoryService` into six deterministic `Pattern`s: repeated tasks and missed deadlines (reusing `taskAnalysis.ts`'s `groupRelatedTasks`/`findOverdue` directly), frequently used workflows and recurring approvals (via `ai-engine`'s generic `detectRecurringPatterns`, keyed by `workflowKey`/`actionType`), and two 7-day-windowed trends (workspace activity, memory usage, via `ai-engine`'s `detectTrend`). `proactiveIntelligenceService.ts` (`ProactiveIntelligenceService.getSuggestions`/`detectPatterns`) maps a curated subset of those patterns into a unified, ranked `Suggestion` (workflow/execution/memory/task/integration) — trend patterns are reported but never turned into a suggestion, since a trend alone doesn't imply one specific action. Every method is a plain read; nothing here ever creates, executes, sends, or connects anything.
- **`src/embeddings/`** — Semantic Search & Context Retrieval (Phase 3.6, docs/decisions/0021-semantic-search-and-context-retrieval.md), over the generic `embeddings`/`embedding_models` tables (`database/migrations/0019_embeddings.sql`) — deliberately separate from `memory_records.embedding`/`document_chunks.embedding`, which already have their own columns and retrieval paths. `chunkingService.ts` (`ChunkingService`) reuses `knowledge/chunking.ts#chunkDocument` directly. `embeddingService.ts` (`EmbeddingService.indexContent`) chunks, hashes (sha256) each chunk, and only re-embeds (calling the injected `EmbeddingProvider`) a chunk whose hash actually changed — unchanged chunks are skipped, stale trailing chunks are deleted. `retrievalService.ts` (`RetrievalService`) provides `search` (ranked cosine similarity, optionally filtered by `source_type`), `getContext` (merges `MemoryService.getWorkspaceContext` with conversation/task search results into an advisory `RetrievedContext`), and `reindexWorkspace` (walks `conversations`/`tasks` via direct SQL — deliberately not through `ConversationService`/`TaskService`, since `ConversationService` depends on `RetrievalService`, and the reverse would cycle). Never calls an AI provider — only the injected `EmbeddingProvider` abstraction.
- **`src/execution/`** — the Action Execution Foundation (Phase 2.6, docs/decisions/0014-action-execution-foundation.md), extended with three Calendar write executors in Phase 2.7. `types.ts`/`errors.ts`/`registry.ts` (`ExecutionRegistry`) mirror the `WorkflowHandler`/`WorkflowRegistry` provider-abstraction pattern: an `ActionExecutor` interface (`actionType`, `provider`, `execute`) and a `Map`-based registry seeded with all seven built-in executors. `executors/` holds one `ActionExecutor` per built-in action — `GmailSendEmailExecutor`/`GmailSaveDraftExecutor`, `GitHubCreateIssueExecutor`/`GitHubCreatePullRequestExecutor`, and (Phase 2.7) `CalendarCreateEventExecutor`/`CalendarUpdateEventExecutor`/`CalendarDeleteEventExecutor` backing three new Tier 3 tier-locked capabilities (`create_calendar_event`/`update_calendar_event`/`delete_calendar_event`) — each composing `IntegrationService` for decrypted credentials and its provider's connector, no new persistence of its own. `executionService.ts` (`ExecutionService`) owns `preview`/`createExecutionRequest`/`execute`/`listHistory`/`getExecution` over the `executions` table (`database/migrations/0014_executions.sql`): `preview` is pure and read-only, and as of Phase 2.7 also surfaces the connected integration's live `tokenExpiresAt` (item 7: "conversation previews include live provider metadata") without ever decrypting or exposing the token itself; `createExecutionRequest` persists and evaluates approval via `ApprovalEngine.evaluate` but never contacts a provider, rejecting up front if the integration isn't connected; `execute` advances at most one attempt per call (mirroring `WorkflowService.executeNextStep`) and is idempotent on a terminal `succeeded`/`failed` record — a retry never re-contacts the provider — and always re-checks approval fresh via `ApprovalEngine.get`, never trusting state captured at creation time. `executionIntentMatcher.ts` (`ExecutionIntentMatcher`) is a pure, rule-based matcher (mirroring `WorkflowIntentMatcher`) wired into `ConversationService`, attaching an advisory `ExecutionSuggestion` to chat responses — never itself creating or running an execution, and deliberately allowed to co-fire alongside a `WorkflowSuggestion` on the same message.
- **`src/routes/`** — HTTP endpoints. `health.ts` reports the `HealthService` result; `capabilities.ts` is foundation-stage; `ai.ts` is an explicitly-labeled smoke-test endpoint predating the real pipeline; `memories.ts` wires memory creation through the `PermissionEngine`/`ActionLogger` and exposes search + workspace-context retrieval, plus (Phase 3.4) list/update/archive/delete over the same `memory_records`; `documents.ts` exposes the document lifecycle API; `tasks.ts` exposes the Task Foundation CRUD API; `drafts.ts` exposes the Action Preparation Layer CRUD API; `approvals.ts` exposes `list`/`get`/`approve`/`reject` over `pending_approvals` — deliberately no public "create" route (docs/decisions/0007-intent-and-approval-workflows.md #4); `users.ts`/`workspaces.ts`/`preferences.ts` expose the User Profile, Workspace Configuration, and Preference Memory Layer APIs (Phase 1.8); `integrations.ts` exposes list/connect/disconnect/rotate over the three fixed providers (Phase 2.3) — deliberately no route to actually read data through a connector, per that phase's "no automation execution" scope; `oauth.ts` exposes the OAuth Framework's two routes (Phase 2.7): `POST .../integrations/:provider/oauth/start` (returns an authorization URL as JSON — the client opens it itself) and the one route in this entire API that isn't workspace-nested in its path, `GET /api/oauth/:provider/callback`, since the provider redirects the user's browser there directly with only `code`/`state` as query parameters; `workflows.ts` exposes workflow definition listing plus create/get/execute/pause/resume/cancel over `workflow_runs` (Phase 2.4); `insights.ts` exposes the four Productivity Intelligence reads — `briefing`, `task-intelligence`, `conversations/:id/intelligence`, `insights` (Phase 2.5) — every one a plain `GET` with no capability gate; `executions.ts` exposes preview/create/execute/list/get over `executions` (Phase 2.6) — `execute` advances at most one attempt per call, same as `workflows.ts`'s execute route; `voice.ts` exposes session start/end/list/get plus a dedicated turn route (`POST .../voice/sessions/:id/turns`, audio in as base64, audio out as base64) over `voice_sessions`/`voice_turns` (Phase 3.2) — no route here is ever invoked automatically, every session requires an explicit start/end call; `conversations.ts` exposes conversation creation, listing (`GET /workspaces/:workspaceId/conversations`, Phase 2.1, newest-active-first), history, and message sending (the real pipeline, now delegating to `AimaCoreService` including real approval creation, plus advisory workflow, execution, and (Phase 3.4) memory suggestions — the last from `RuleBasedMemoryExtractor`, never itself creating a memory); `proactive.ts` (Phase 3.5) exposes `GET .../proactive/patterns` and `GET .../proactive/suggestions` over `ProactiveIntelligenceService` — mounted only when that service is supplied (an optional `AppDependencies` field, so no existing route test needed updating); `retrieval.ts` (Phase 3.6) exposes `GET .../retrieval/search`, `GET .../retrieval/context`, and `POST .../retrieval/reindex` over `RetrievalService` — mounted the same conditional way, and unlike `memories.ts`/`documents.ts`'s own read routes, all three are explicitly permission-gated (`semantic_search` for the two GETs, `reindex_embeddings` for the reindex POST) per this phase's explicit requirement.
- **`src/voice/`** — the Voice Assistant Foundation (Phase 3.2, docs/decisions/0017-voice-assistant-foundation.md), extended with a real provider in Phase 3.3 (docs/decisions/0018-real-voice-provider-integration.md). `types.ts`/`errors.ts` define `VoiceSession`/`VoiceTurn`/`Transcript`/`VoiceConfiguration`, the lifecycle errors, and `VoiceProviderError` (Phase 3.3) — thrown when the configured `SpeechToTextProvider`/`TextToSpeechProvider` fails or times out, wrapping the real cause with a generic message so a vendor's raw error body never reaches the client. `voiceService.ts` (`VoiceService`) is a thin wrapper around the existing conversation pipeline — `startSession` creates a real, listable `conversations` row (via the unmodified `ConversationService.createConversation`) and a `voice_sessions` row pointing at it; `submitVoiceRequest` transcribes the caller's audio via an injected `SpeechToTextProvider`, runs the transcript through `ConversationService.sendMessage` unmodified (so context assembly, intent detection, and approval evaluation all apply exactly as they do to a typed chat message), then synthesizes the reply via an injected `TextToSpeechProvider` — no audio is ever persisted, only the transcript text and response text (`voice_turns`, `database/migrations/0016_voice.sql`). `endSession`/`getSession`/`listSessions`/`listTurns` round out the lifecycle, all workspace-isolated the same way every other service in this codebase is.
- **`src/testUtils/`** — shared test helpers (transaction-scoped test DB access, workspace/conversation seeding, capability syncing), plus `fakeFetch.ts` (Phase 2.7) — a queued-response, injectable stand-in for `fetch` every live connector and OAuth provider test uses, so none of them ever makes a real network call.
- **`src/app.ts`** — builds the Express app from injected dependencies (testable without a live database).
- **`src/index.ts`** — process entry point: loads config, syncs capabilities to the DB, wires dependencies, starts listening.

## What's intentionally not built yet

The following are deliberately out of scope until later sprints and are called out with `TODO`/doc-comments in the relevant files:

- Authentication and session management.
- Per-workspace permission tier overrides (`workspace_capability_settings`) — capability tiers currently resolve to their code-registered default only, so `AimaCoreService`'s automatic approval creation (Phase 1.7) has no real Tier 3 capability to exercise yet under shipped defaults.
- A real, registered OAuth app for Google or GitHub, and a live end-to-end test against real accounts — the full OAuth framework, live connectors, and encrypted token storage/refresh/rotation are all implemented and tested against a fake `fetch` (Phase 2.7, docs/decisions/0015-live-integration-providers.md), but registering an actual OAuth app and reaching a live provider over the network is outside what this environment can do (Integration Sprint). `read_email` (`summarize_unread_email`, Phase 2.4) and all seven Phase 2.6/2.7 execution capabilities (`send_email`, `draft_gmail_email`, `create_github_issue`, `create_github_pull_request`, `create_calendar_event`, `update_calendar_event`, `delete_calendar_event`) now have real callers exercising the Tier 3 approval path; `read_repositories`/`read_calendar` remain registered with no caller — the same "ready but not yet exercised" state.
- Workflow execution beyond one step at a time — `WorkflowService.executeNextStep` is deliberately not a "run to completion" call; a client (or a future scheduler) must drive each step, which is what keeps "pause" meaningful and "no automatic execution" a structural property rather than a convention (Phase 2.4, docs/decisions/0012-workflow-orchestration-foundation.md).
- Execution beyond one attempt at a time — `ExecutionService.execute` is deliberately not a retry loop; it advances at most one attempt per call and is idempotent on a terminal record, mirroring `WorkflowService.executeNextStep`'s "no automatic execution" property (Phase 2.6, docs/decisions/0014-action-execution-foundation.md). No autonomous agents, scheduled execution, background workers, automatic retries, streaming execution, multi-action execution, background sync, push notifications, webhooks, or automatic polling exist or are implied by any phase through 2.7.
- Real PDF text extraction — `PdfDocumentParser` is a stub that fails clearly; the format is recognized end-to-end so a real implementation is a drop-in later.
- Token-level response streaming to the client — `POST .../messages` currently returns one JSON response once the full completion is ready.
- Wake word detection, background/always-listening audio capture, and autonomous multi-turn voice conversation — explicitly out of scope for both the mock and real (`openai`, Phase 3.3) voice providers; every voice turn requires an explicit client call with already-captured audio (docs/decisions/0017-voice-assistant-foundation.md, docs/decisions/0018-real-voice-provider-integration.md). Only OpenAI's Whisper/TTS REST APIs are implemented as a real vendor today — a second vendor is a drop-in `SpeechToTextProvider`/`TextToSpeechProvider` implementation later, no call-site changes.
- Scheduled invitation expiry — `InvitationService.expirePendingInvitations(olderThanDays)` (Invitation Acceptance & Lifecycle sprint) is a sweep, not a cron job; this codebase has no scheduling infrastructure, and none was introduced for this. Call it manually (a one-off script, a REPL against the running process, or a future admin action) whenever stale pending invitations should be marked `expired` — it's idempotent, so re-running it is always safe.

## Running locally

See `docs/DEVELOPMENT_SETUP.md` §6. Quick reference:

```bash
cp .env.example .env   # then fill in DATABASE_URL, CREDENTIAL_ENCRYPTION_KEY, etc.
npm run dev             # from repo root: npm run dev --workspace=backend
```

`SPEECH_TO_TEXT_PROVIDER`/`TEXT_TO_SPEECH_PROVIDER` (Phase 3.2) both default to `mock`, so voice sessions work out of the box with no vendor account — see `src/voice/`.

`CREDENTIAL_ENCRYPTION_KEY` (Phase 2.3) is required at startup, the same way `DATABASE_URL` is — generate one with `openssl rand -base64 32`. `PUBLIC_BACKEND_URL`, `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET`, and `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET` (Phase 2.7) are likewise required — see `docs/DEVELOPMENT_SETUP.md`'s "OAuth Configuration" section for how to register the two OAuth apps these come from.

`GET /health` reports database, AI provider, memory, knowledge, (Phase 3.1) integration-readiness, and (Phase 3.3) voice-provider status (`HealthService`).

Running in production? See `docs/PRODUCTION_SETUP.md` (Phase 3.1) for `NODE_ENV=production`, database TLS/pooling, logging, error monitoring, and a Docker build — `backend/.env.production.example` is the production environment template.

Tests connect to a real Postgres database (default `postgresql://postgres:postgres@127.0.0.1:5432/aima_test`, override via `TEST_DATABASE_URL`) — see `docs/DEVELOPMENT_SETUP.md` §7. Tests exercising `ApprovalEngine` call `seedCapabilities()` (`src/testUtils/db.ts`) first, since it depends on the `capabilities` table being populated. Because this database is shared and never reset between runs, tests that need to prove "no capability row exists" register a one-off capability name in an in-memory-only registry rather than assuming the shared `capabilities` table is empty.

Note: `npm test` runs `tsx --test 'src/**/*.test.ts'` with the glob **quoted** — `/bin/sh` on Debian/Ubuntu is `dash`, which doesn't support bash's `**` recursive globstar, so an unquoted pattern silently misses test files more than one directory deep. Keep the quotes if you ever touch this script.
